## 1. 구 F1 0.86 정정 설명

### 1.1 보고용 문구 (그대로 사용 가능)
> 이전에 보고한 F1 0.84~0.86 은 평가 방식의 결함 때문에 **모델 성능을 나타내지 않습니다.** 평가를 다시 설계해 같은 모델(운영 중인 v1)을
> 재측정한 결과 이벤트 단위 F1 은 **0.325**(시뮬레이션 시드 7, 노이즈 포함 데이터 1개) 였습니다. 이후 학습 데이터와 학습 코드의 결함을 고쳐
> **새로 학습한 모델**에 알람 정책을 조정한 결과는 **0.796 ± 0.011**(정책 선택에 쓰지 않은 검증 전용 시드 3개 평균) 입니다.
> 두 수치는 **모델과 평가 데이터가 모두 다르므로** 같은 조건의 개선폭이 아닙니다. 같은 검증 시드 3개에서 새 모델 + 기본 정책은 0.617 ± 0.024 였습니다.
> 장애 신호를 알고 만든 단순 규칙(같은 검증 시드 0.919)보다는 아직 낮으며, 실데이터 성능은 검증되지 않았습니다.

### 1.2 무엇이 잘못되었나 (근거)
| # | 결함 | 결과 | 현재 평가에서의 조치 |
|---|---|---|---|
| 1 | 정답 구간이 너무 넓음 (장애 시작 ~ failure+168h) | 포트×시간의 **93.9%** 가 정답 → 오탐이 구조적으로 거의 불가능. **"항상 알람"이 F1 0.97** | 에피소드가 실제로 활성인 구간(+작은 허용 오차)만 정답 |
| 2 | 사후 알람을 TP 로 인정 | TP 의 **91%** 가 장애 발생 이후 알람 (예지가 아님) | 장애 이전 첫 알람(조기 탐지)과 사후 탐지를 분리 보고 |
| 3 | 알람 단위 정밀도와 시나리오 단위 재현율을 섞은 F1 | 단위가 달라 해석 불가 | 이벤트 단위로 통일 (TP=탐지 에피소드, FP=오탐 인시던트) |
| 4 | 평가 기간이 학습 기간과 겹침 + 학습 데이터에 장애 구간 포함 | 본 데이터를 다시 채점 | 시드 고정 생성기, 학습과 분리된 데이터, 정책 선택용/검증 전용 시드 분리 |
| 5 | 스케일러가 검증 데이터로 다시 fit 된 채 저장 (학습 코드 버그) | 학습·추론 스케일링 불일치, 기존 모든 모델에 영향 | 수정 + 회귀 테스트 (lessons #25) |
| 6 | 베이스라인 없음 | 좋은지 나쁜지 판단 불가 | 항상 알람 / 고정 임계치 / 롤링 규칙을 같은 채점으로 병기 (lessons #23) |

### 1.3 예상 질문
- **"그럼 이전 보고는 틀린 것인가?"** — 숫자 자체는 계산대로 나왔지만, 그 채점 방식에서는 아무 모델이나 높은 점수를 받았으므로 성능의 근거가 될 수 없습니다. 결함은 내부 점검(2026-10-01)에서 "항상 알람" 같은 극단 입력으로 지표를 시험하다 발견했습니다.
- **"0.325 → 0.796 은 같은 잣대인가?"** — 지표(이벤트 F1)는 같지만 **비교 조건은 다릅니다**: 0.325 는 v1 모델 × 시드 7 단일 데이터, 0.796 은 새로 학습한 모델 + 조정된 정책 × 검증 전용 시드 3개 평균입니다. 따라서 "2.4배 개선" 같은 직접 비교는 하지 않습니다. 같은 검증 시드 3개 안에서의 비교는 새 모델 기본 정책 0.617 ± 0.024 → 조정 정책 0.796 ± 0.011 입니다 (`performance_report.md` 2장).

## 2. 정직한 요약 (1페이지)

**한 줄 요약**: 시뮬레이션에서 AI 모델은 고정 임계치보다 낫고 오탐이 적지만, 포트별 롤링 규칙보다는 낮습니다. 실데이터 검증은 아직 하지 않았으며, 이를 위한 합격 기준과 섀도 운영 계획을 제안합니다.

### 2.1 성능 (검증 전용 시드 3개, 평균 ± 표준편차, 시뮬레이션)
| 방법 | 이벤트 F1 | 조기 탐지율 | 리드타임 중앙값 | 오탐/포트·일 | 이벤트 정밀도 |
|---|---|---|---|---|---|
| **AI + 오탐 억제형 정책** (후보, 미적용) | **0.796 ± 0.011** | 65.3% ± 2.1 | 152분 ± 20 | 0.010 ± 0.002 | 90.2% |
| AI + 현재 기본 정책 | 0.617 ± 0.024 | 77.2% ± 1.6 | 205분 ± 7 | 0.100 ± 0.007 | 50.0% |
| 롤링 규칙 (베이스라인) | 0.919 ± 0.006 | 85.4% ± 0.9 | 215분 ± 7 | 0.003 ± 0.001 | 97.1% |
| 고정 임계치 (베이스라인) | 0.720 ± 0.015 | 56.2% ± 1.8 | 170분 ± 14 | 0.000 | 100% |
| 항상 알람 (베이스라인) | 0.558 ± 0.005 | — | — | — | — |
| (참고) 현재 운영 중인 v1 — **시드 7 단일 데이터, 위 행들과 데이터가 다름** | 0.325 | — | — | — | — |

- 지표 정의: 조기 탐지 = 장애(failure) 시점 이전에 첫 알람. 오탐 인시던트 = 어떤 장애 활성 구간에도 속하지 않는 알람을 1시간 간격으로 묶은 것 (`validation/evaluation/metrics.py`).
- 오탐/포트·일의 체감 규모: 포트 1,000개 기준 하루 오탐 건수 = 기본 정책 약 100건, 오탐 억제형 약 10건, 롤링 규칙 약 3건.

### 2.2 강점 / 약점 (가정 민감도, `performance_report.md` 4장)
- **강점**: 노이즈(0~4배), 결측 5%, 장애 빈도(평균 2일 ~ 21일 간격) 변화에 F1 기준으로는 0.79~0.82 로 거의 영향 없음 (단, 장애 잦음 조건의 오탐은 0.038 로 기준 조건 0.012 의 약 3배).
- **약점**: 트래픽 감소 위주 장애에서 F1 0.40·조기 탐지 24.6%(최저, 롤링 규칙도 F1 0.72 로 취약), 약한 장애에서 조기 탐지 29.6%. 가정에 따라 **F1 0.40 ~ 0.84, 조기 탐지 25% ~ 82%** 범위.
- **상충**: 오탐 억제형 정책은 오탐을 10분의 1로 줄이는 대신 조기 탐지 77% → 65%, 리드타임 205 → 152분. 어느 쪽을 중시할지는 현장 정책 결정.

### 2.3 현재 운영 상태 (사실)
- 운영 중인 모델은 결함이 있는 구 모델 v1 이며 기본 정책입니다. 개선 모델과 오탐 억제형 정책은 **아직 적용하지 않았습니다** (P1-3 에서 승격 결정).
- 재학습 결과는 후보로만 저장되고 사람의 승격으로만 활성화됩니다 (P0-1). 수동 롤백 가능.
- 파이프라인(Producer → Kafka → Consumer → DB → API → UI)은 로컬 컨테이너 E2E 에서 검증했습니다. GPU 서버(arm64) 배포, 브라우저 화면 동작은 미검증입니다.

### 2.4 AI 모델이 롤링 규칙보다 낮은데 왜 계속하는가 (보고 시 예상되는 질문)
솔직한 답: **시뮬레이션에서는 아직 근거가 없습니다.** 롤링 규칙의 임계값은 시뮬레이터가 만드는 장애 범위를 알고 정했기 때문에 시뮬레이션에서 유리하지만,
실데이터에서는 규칙이 가정하지 못한 장애 모양이 있을 수 있고 AI 는 다변량 패턴을 학습으로 잡는다는 가설이 있습니다. 이 가설은 **실데이터 섀도 운영에서
두 방법을 같은 기간에 나란히 비교**해서만 확인할 수 있으며(4.2 "롤링 규칙 대비" 보고 항목), 결과에 따라 규칙 + AI 하이브리드(P1-4)나 규칙 우선 운영도 선택지로 둡니다.

## 3. 시뮬레이션 수치의 한계 (보고서에 반드시 포함)
1. **장애 모양·노이즈·유병률이 모두 가정**입니다. 시뮬레이터가 만든 장애(CRC 증가, 광 열화, 트래픽 감소 등)만 평가했고, 실제 망에서 흔한 장애 유형의 비율은 모릅니다.
2. **정상 교란의 종류가 제한적**입니다. 버스트/산발 에러/광 흔들림/결측만 넣었습니다. 계획 작업, 회선 증설, 계절성 트래픽 변화 같은 실제 정상 변동은 포함되지 않았습니다 (lessons #24: 학습 분포에 없던 정상 교란이 오탐의 주원인이었음).
3. **롤링 규칙은 중립적인 비교 대상이 아닙니다** (임계값을 시뮬레이터를 알고 정함). 실데이터에서 순위가 바뀔 수 있습니다 — 어느 방향으로든.
4. **선택 정책은 개선 모델과 짝**이며 운영 중인 v1 에는 맞지 않습니다.
5. 검증 전용 시드는 3개, 민감도 시드는 2개입니다. 표준편차는 시뮬레이터의 무작위성만 반영하며, 가정 자체가 틀렸을 때의 오차는 반영하지 않습니다 (그래서 민감도 범위 0.40~0.84 를 함께 보고).
6. 15분 단위 데이터에서 평가했으며 실 장비의 수집 지연·누락 패턴은 반영되지 않았습니다.

## 4. 실데이터 합격 기준 (제안값 + 근거)

### 4.1 전제
- 실데이터에는 정답(장애 라벨)이 없으므로 **정답이 필요 없는 지표**(알람 부하, 현장 검토 유효율)를 주 기준으로 하고, EMS 장애 알람(LOS/Link Down 등)을 **약한 정답**으로 쓰는 지표는 이벤트 수가 충분할 때만 판정에 씁니다.
- 기준은 **데이터를 보기 전에 합의**합니다 (lessons #30). 섀도 판정 기간 중에는 기준을 바꾸지 않습니다.
- "인시던트" 정의는 시뮬레이션 평가와 같게 둡니다: 같은 포트에서 1시간(4스텝) 이내로 이어진 알람을 1건으로 묶음.
- 단위 구분: **알람 인시던트** = 방법이 낸 전체 인시던트(장애·오탐 포함, 정답 없이 셀 수 있음). **오탐 인시던트** = 그중 무효로 판정된 것(현장 검토로 추정). 시뮬레이션 표의 "오탐/포트·일"(2.1)은 후자입니다.
- 모든 기준은 **판정 기간(동결된 2주 + 필요 시 연장, 5.3)** 의 데이터로만 계산합니다. 개발 기간 데이터는 판정에 쓰지 않습니다.

### 4.2 기준표
| ID | 지표 | 제안 기준 (합격) | 근거 | 판정 조건 |
|---|---|---|---|---|
| **C1** | **추정 오탐 부하** = 알람 인시던트/포트·일 × (1 − C2 점추정) | **≤ 0.02 건/포트·일** (1,000포트 기준 하루 20건 이하) | 시뮬레이션 정책 선택 규칙의 오탐 상한과 동일. 선택 정책 실측 오탐 0.010 의 2배 여유. 기본 정책(오탐 0.100)은 불합격 수준 | C2 와 같은 샘플로 계산. 상한과 별도로 **운영 인력이 하루에 검토 가능한 알람 건수**를 절대값으로 합의 (6.1) |
| **C2** | **현장 검토 유효율** = 유효 / (판단 불가를 뺀 AI 샘플) | **Wilson 95% 하한 ≥ 50%** (2026-10-06 확정, 6.1). 목표: 점추정 70% (기존 알람 헛알람 비율 확인 시 조정 가능) | 시뮬레이션 이벤트 정밀도: 선택 정책 90%, 기본 정책 50%. 실데이터는 정상 교란이 다양해 낮아질 것으로 예상. 50% 미만은 "알람의 절반 이상이 헛것"이라 운영자가 알람을 무시하게 됨(알람 피로) | 판정 가능한 AI 샘플 **≥ 100건** (부족 시 판정 기간 연장, 5.3). 참고: n=100 에서 하한 50% 를 넘으려면 점추정 약 60% 이상 필요 |
| **C3** | **선행 탐지율 (약한 정답)** = EMS 장애 알람 이벤트 중, 이전 24시간 ~ 15분 사이에 같은 포트의 AI 알람이 있었던 비율 | **≥ 30% (최소), 목표 50%** | 시뮬레이션 조기 탐지: 선택 정책 기준 65.3%, 민감도 조건 중 최저는 트래픽 감소 위주 24.6%, 약한 장애 29.6% (`performance_report.md` 4장). 실데이터에는 예고 없이 발생하는 장애(절단 등)가 섞여 있어 상한 자체가 낮음 | EMS 이벤트 **≥ 20건**일 때만 판정. 미만이면 참고치로 보고하고 **C3 판정 보류** |
| **C4a** | **고정 임계치 대비 유효 탐지량** = 알람 인시던트 수 × 유효율 (같은 기간·같은 포트) | AI > 고정 임계치 | 자명한 방법을 못 이기면 가치가 없음 (lessons #23). 유효율 자체는 비교하지 않음: 시뮬레이션에서도 고정 임계치는 정밀도 100%·조기 탐지 56% 로, AI 의 가치는 **더 많이 맞게 잡는 것**(정밀도가 아닌 탐지량)에 있음 | 정답 없이 판정 가능 (C3 와 무관). 고정 임계치 인시던트도 블라인드 검토 (4.3). 고정 임계치 샘플은 판정 기간 약 30건이라 불확실성이 큼 → **유효 탐지량 = 인시던트 수 × 유효율의 Wilson 95% 구간**으로 비교: AI 하한 > 고정 상한이면 **충족**, AI 상한 < 고정 하한이면 **미충족**, 구간이 겹치면 **동률(유의한 차이 없음)** (4.4) |
| **C4b** | **고정 임계치 대비 선행 탐지** | AI 의 C3 > 고정 임계치의 C3 | 예지 목적 | **C3 판정 시에만 판정**, C3 보류면 C4b 도 보류 |
| (보고) | 롤링 규칙 대비 | 판정에 쓰지 않음 | 시뮬레이션에서 롤링 규칙은 중립적 비교 대상이 아님 (3장 3) | C4a·C4b 와 같은 방식으로 계산해 병기 + "규칙이 못 잡은 유효 인시던트 수(AI 추가 탐지)" → P1-4 하이브리드 결정 근거 |
| **C5** | **운영 무결성** (세 항목 모두) | **C5a 처리율** = 저장된 결과 행 / 처리 대상 행 ≥ 99.9% · **C5b 지연** = 저장된 행의 99% 이상이 `detect_time − occur_date` ≤ 30분 · **C5c 중단** = 서비스 중단 누적 ≤ 1시간이며 모두 자동 복구 | 결과가 아무리 좋아도 파이프라인이 누락·지연하면 무의미. **처리 대상 행** = 원본 성능 데이터에 운영과 같은 `DataProcessor`(전처리 + 시퀀스 생성)를 적용했을 때 **추론 윈도우가 만들어지는 행**. 워밍업 구간과, 2스텝 이상 연속 결측이 윈도우에 걸려 시퀀스가 제외되는 행(정상 동작, `data_processor.py` 의 NaN 윈도우 제외, lessons #18)은 분모에서 뺌. 배치 재구성과 스트리밍 윈도우의 동등성은 검증됨(lessons #26). 결측 때문에 제외된 행의 비율은 별도 참고치로 보고. C5b 의 30분은 수집 주기 15분 + 처리 여유 15분 (EMS 수집 지연의 실제 분포를 모르므로 개발 기간에 측정한 뒤 **판정 기간 시작 전에** 확정). **C5b 는 라이브 가동 데이터에서만 유효**: `detect_time` 은 DB 저장 시점(`datetime.now()`, `db_connector.py`)이라 오프라인 재생 결과로는 계산하지 않음 | 판정 기간 전체. **C5 미충족은 모델 판정이 아니라 "판정 무효"** (4.4) |
| **C6** | **알람량 안정성** = 일별 알람 인시던트 수 | 망 이벤트가 없는 날 중, 판정 기간 중앙값의 0.5 ~ 2배를 벗어난 날 **≤ 2일** | 학습 분포 밖 정상 변동에 민감한지 확인 (lessons #24) | **망 이벤트일** = 운영 측 작업/장애 기록(계획 작업, 대규모 장애)에 있는 날로, **알람량을 보고 정하지 않음**(순환 방지). 망 이벤트가 없는 날이 10일 미만이거나 일별 중앙값이 10건 미만이면 C6 판정 보류. 중앙값 10건 하한의 근거: 알람 수가 무작위(포아송)로만 변해도 0.5~2배를 벗어나는 날이 평균 5건/일이면 14일 중 약 1.9일(기준 2일과 같아 구분 불가), 10건/일이면 약 0.4일, 20건/일이면 약 0.1일. 파일럿 규모 예(보수적 예시: 오탐 상한 0.02 만큼만 알람이 난다고 가정, 실제 전체 알람은 유효 알람이 더해져 이보다 많음): 1,000포트 × 0.02건/포트·일 = 20건/일이므로 **항상 보류되는 조건은 아니며**, 500포트 미만·알람이 매우 적은 경우에만 보류됨 |

### 4.3 현장 검토 분류 (C2 의 분모·분자)
| 분류 | 의미 | C2 계산 |
|---|---|---|
| 유효-장애 | 실제 장애/열화 확인 (EMS 알람·티켓·조치 이력 있음) | 유효 |
| 유효-예방 | 장애는 아니지만 점검·조치가 필요한 이상 (예: 광 레벨 저하 추세) | 유효 |
| 정상 변동 | 원인은 있으나 조치 불필요 (계획 작업, 트래픽 패턴 변화, 회선 증설) | 무효 (별도 집계 → 정상 교란 학습 데이터 후보) |
| 오탐 | 원인 없음 | 무효 |
| 판단 불가 | 정보 부족 | 분모에서 제외 (단, 30% 초과 시 샘플 정보 보강 후 재검토) |

**샘플링 (주 단위, 블라인드)**
| 대상 | 개발 기간 (1~2주차) | 판정 기간 (3주차~) | 용도 |
|---|---|---|---|
| AI 인시던트 | 주 30건 | **주 50건** | C1, C2, C4a |
| 고정 임계치 인시던트 (오프라인 재생) | 주 10건 | **주 15건** | C4a |
| 롤링 규칙 인시던트 (오프라인 재생) | 주 10건 | 주 10건 | 보고 |

- 각 방법의 인시던트에서 심각도별 층화 무작위 추출, **포트당 최대 3건**. 해당 주 인시던트가 할당량보다 적으면 전수 검토.
- 세 방법의 샘플을 섞고 방법 이름을 숨긴 ID 로 검토(블라인드). 같은 포트에서 시간이 겹치는 인시던트는 한 번만 검토하고 라벨을 공유.
- 판정 기간 2주 = AI 판정 가능 샘플 약 100건(판단 불가 비율에 따라 부족할 수 있음 → 5.3 연장 규칙). 검토 부담 주 약 75건 ≈ 건당 2분 기준 2~3시간/주.

### 4.4 판정 결과와 다음 행동
위에서부터 **처음 해당하는 행**을 판정으로 합니다.

| 순서 | 결과 | 조건 | 다음 행동 |
|---|---|---|---|
| 1 | **판정 무효** | C5 미충족 | 파이프라인 결함 수정 후 판정 기간을 처음부터 다시 시작 (모델 성능 판정 아님) |
| 2 | **불합격** | C2 점추정 < 40% · 또는 C4a 미충족(AI 상한 < 고정 하한) · 또는 C4b 미충족(판정 시) · 또는 **C1 초과이고 정책 조정으로 해결 불가**(아래 정의) | 규칙 우선 운영 + AI 보조 등 구조 재검토 (P1-4), 실데이터로 재학습 검토 |
| 3 | **조건부** | C2 미달(Wilson 하한 < 50%)이지만 점추정 ≥ 40% · 또는 C1 초과이고 정책 조정으로 해결 가능 · 또는 C4a 동률(구간 겹침) · 또는 C3 미충족(판정 시) · 또는 C6 미충족 | 개발 기간 데이터로 정책 재선택(또는 원인 분석) → **새 판정 기간**으로 재평가 (같은 주 데이터로 재판정 금지) |
| 4 | **합격** | C1·C2 충족, C4a 충족(AI 하한 > 고정 상한), C3·C4b·C6 는 충족 또는 판정 보류 | 알람 운영 연동 단계로 (범위 확대 섀도 또는 제한적 실운영). **C3 가 보류면 "합격(예지 성능 미검증)"으로 표기**하고 보고서에 명시 |

- **"정책 조정으로 해결 가능"의 판정 방법** (주관 배제): 판정 기간 데이터에 대안 정책(현재 프리셋 2종 + 임계치 배율 격자)을 오프라인 재생해, 검토 라벨이 있는 인시던트로 추정한 C1 ≤ 0.02 **와** C2 하한 ≥ 50% 를 동시에 만족하는 정책이 하나라도 있으면 "가능", 없으면 "불가". 대안 정책이 만든 인시던트 중 라벨이 없는 것은 미검토로 두고 그 비율을 함께 보고합니다(30% 초과 시 "가능" 판정은 개발 기간 재검토 후에만 인정). 이 재생 결과로 고른 정책은 **새 판정 기간에서 다시 확인**해야 합니다 (lessons #30).

## 5. 섀도 운영 계획

### 5.1 정의와 현재 구조에서의 의미
- **섀도 운영** = 실제 망 데이터로 시스템을 그대로 가동하되 **알람에 따른 조치는 하지 않고**, 주간 검토로만 결과를 평가하는 기간.
- 현재 알람 전달 경로는 Consumer → 내부 API(`/api/internal/alarm`) → 대시보드 SSE 뿐이며 외부 NMS/티켓 연동은 없습니다 (`src/pipeline/kafka_consumer.py:133`). 따라서 **섀도를 위한 코드 변경은 필요 없고**, 운영 절차로 "조치 없음"을 보장합니다. 대시보드 접근은 검토 담당자로 제한을 권장.
- 운영 중에는 모델 1개·정책 1개만 돈다. 대안 정책과 베이스라인(고정 임계치, 롤링 규칙)은 같은 기간 DB 데이터를 **오프라인으로 재생**해 비교합니다 (P1-2 `real_data_check` 의 기능, 6.2).

### 5.2 선행 조건
| 조건 | 상태 | 비고 |
|---|---|---|
| 합격 기준 합의 (4장, 6.1) | 임시 확정 (2026-10-06) | C1 상한·C2 목표는 현장 정보 확인 후 섀도 시작 전까지 조정 가능 |
| 평가 대상 모델·정책 확정 (P1-3: 개선 모델 승격 + 정책 프리셋 결정) | 미완 | v1 로 섀도를 하면 결함 모델을 평가하게 되므로 권장하지 않음. 일정상 불가피하면 1~2주차(개발 기간)만 v1 로 시작 가능 |
| `real_data_check` 도구 (P1-2) | 미완 | 6.2 요구사항 |
| EMS 알람 이력 추출 경로 (약한 정답) | 미확인 | 없으면 C3 판정 보류로 진행 |
| 섀도 중 자동 재학습 차단 | 가능 | 드리프트 재학습은 이미 후보 저장만 함(P0-1). P1-1 이후에는 `DRIFT_RETRAIN_MODE=off` 로 고정 |
| GPU 서버(arm64) 배포 확인 (P2-4) | 미완 | 섀도를 GPU 서버에서 할 경우 선행 |

### 5.3 범위와 기간
- **범위(제안)**: 1~2개 지역, 포트 500 ~ 2,000개. 최근 6개월 내 장애 이력이 있는 장비를 포함해 C3 이벤트 수를 확보.
- **기간(제안)**: 기본 5주 (연장 규칙 적용 시 최대 7주)
  | 주차 | 구분 | 내용 |
  |---|---|---|
  | 0 | 준비 | 파일럿 포트 확정, 학습 구간 확인, 모델·정책·RCA 룰 버전 기록, 검토자 지정, 검토 양식 배포 |
  | 1 ~ 2 | **개발 기간** | 주간 검토 시작(4.3 개발 기간 할당량). 운영 이슈(누락, 지연) 수정과 정책 재선택을 **허용**. C5b 지연 기준을 실측 분포로 확정. 이 기간 결과는 판정에 쓰지 않음 |
  | 3 ~ 4 | **판정 기간** | 모델·정책·룰 **동결**. 변경하면 판정 기간을 처음부터 다시 시작 |
  | 5 | 판정 | 4장 기준으로 판정, 보고서 작성 |
- **연장 규칙** (시작 전에 합의, 판정 기간 중 동결 유지):
  1. 판정 기간 2주 종료 시 C2 의 판정 가능 AI 샘플이 100건 미만이면, 100건이 찰 때까지 **주 단위로 최대 2주** 연장. 그래도 미달이면 그 시점 샘플로 판정하고 샘플 수와 신뢰구간을 보고서에 명시.
  2. C3 의 EMS 이벤트가 20건 미만이면 주 단위로 **최대 2주** 연장. 규칙 1 과 같은 연장 기간을 공유하며 따로 더하지 않음. 그래도 미달이면 C3·C4b 판정 보류.
  3. C6 는 연장된 기간을 포함해 계산.
  - **상한은 "판정 기간 총 4주"** (기본 2주 + 연장 최대 2주, 규칙 1·2 공통). 전체 섀도 기간은 개발 2주 + 판정 2~4주 + 판정 작업 1주 = **5 ~ 7주**이며, 준비(0주차) 1주는 가동 전이라 이 기간에 넣지 않음.

### 5.4 주간 절차
1. (월) `real_data_check` 로 지난주 구간 실행 → 포트·일당 알람 인시던트(AI·고정·롤링), 일별 인시던트 수, 심각도 분포, 상위 알람 포트, C5 처리율·지연, 블라인드 검토 샘플 CSV(4.3 할당량).
2. (화~목) 현장 엔지니어가 샘플 분류 (4.3 분류, 블라인드). 개발 기간 주 약 50건, 판정 기간 주 약 75건 (2~3시간/주).
3. (금) 누적 집계 → 주간 1페이지 리포트: C1·C2(점추정 + Wilson 하한)·C4a·C5 추이, 일별 알람량(C6), 연장 규칙 해당 여부, 상위 오탐 포트와 원인 유형, "정상 변동" 사례 목록.
4. 운영 측은 계획 작업·대규모 장애 발생일을 **당일 기록** (C6 의 망 이벤트일, 사후에 알람량을 보고 추가하지 않음).
5. 판정 기간에는 수치만 기록하고 설정을 바꾸지 않습니다.

두 종류로 구분합니다. **[중단]** = 즉시 섀도 가동을 멈춤. **[경보(검토 후 결정)]** = 가동은 계속하고 운영 책임자가 조치를 결정.
- **[중단]** DB 쓰기 부하나 수집 지연이 운영 EMS 에 영향을 줄 때
- **[경보(검토 후 결정)]** 알람 인시던트(전체, AI) 가 0.04 건/포트·일을 3일 연속 초과 → 개발 기간이면 정책 조정, 판정 기간이면 기록 후 판정 기간 재시작 여부를 결정.
  - 0.04 = C1 상한 0.02 ÷ (1 − C2 최소 유효율 0.5). 유효율이 50% 라면 C1 을 위반하는 알람량이며, 검토 결과를 기다리지 않고 알람 수만으로 조기에 감지하기 위한 값입니다. 유효율이 더 높으면 0.04 를 넘어도 C1 은 충족할 수 있으므로 [중단]이 아닌 [경보]입니다.
- **[경보(검토 후 결정)]** 처리율(C5a)이 하루라도 99% 미만 (C5 기준 99.9% 보다 한 단계 느슨한 즉시 대응선) → 원인 파악. 판정 기간이면 C5 미충족 가능성이 높으므로 판정 무효(4.4) 처리 여부를 결정.

### 5.7 종료 산출물

### 6.2 P1-2 (`real_data_check`)에 대한 요구사항 (이 문서에서 도출)
- 입력: DB 기간, 포트 필터(파일럿 포트 목록), 선택적 EMS 알람 이력 파일
- 출력:
  - 포트·일당 **알람 인시던트** 수(인시던트 정의는 `validation/evaluation/metrics.make_incidents` 와 동일하게 1시간 묶음), 심각도·포트별 분포 (C1, 5.6 경보 0.04)
  - **일별** 알람 인시던트 수 + 망 이벤트일 목록(입력 파일)을 받아 C6 계산 (중앙값 대비 0.5~2배 이탈 일수, 보류 조건)
  - 같은 기간 고정 임계치·롤링 규칙의 오프라인 알람과 인시던트 수, AI 와 규칙의 겹침/차집합 (C4a, 보고)
  - 층화 샘플 CSV: 방법별 할당량(4.3), 포트당 최대 3건, 세 방법을 섞은 **블라인드 ID**, 겹치는 인시던트 라벨 공유, 검토 분류 컬럼(4.3)
  - 검토 결과 CSV 를 다시 읽어 방법별 누적 유효율(점추정 + Wilson 95% 신뢰구간), 추정 오탐 부하(C1), 유효 탐지량(C4a), 판정 가능 샘플 수와 연장 규칙 해당 여부 (C2)
  - EMS 이력이 있으면 방법별 선행 탐지율과 리드타임 (C3, C4b, 이벤트 수 < 20 이면 "판정 보류" 표시)
  - **C5**: 처리 대상 행(원본 데이터에 운영과 같은 `DataProcessor` 를 적용해 추론 윈도우가 만들어지는 행 — 워밍업·결측 윈도우 제외) 대비 `anomaly_detection` 저장 행 비율(C5a), 결측으로 제외된 행 비율(참고), `detect_time − occur_date` 분포와 30분 이내 비율(C5b, 라이브 가동 구간만), 결과가 1시간 이상 비어 있는 구간 목록(C5c 근거)
  - C4a: 방법별 유효 탐지량과 Wilson 95% 구간, 충족/동률/미충족 표시
  - 대안 정책 오프라인 재생(4.4 "정책 조정으로 해결 가능" 판정): 정책별 추정 C1·C2 하한, 미검토 인시던트 비율
- 정답 없이 동작해야 하며, 운영 코드(`src`)는 이 도구를 import 하지 않음 (`validation/` 배치).
