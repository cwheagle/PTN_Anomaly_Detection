# 탐지 타겟 정의 (잠정)

> 작성: 2026-10-15 · 상태: **잠정 (현장 확인 전)** — 2026-10-14 사용자 합의안(`handoff_target_first.md` 3장)을 문서화한 것. 갱신 2026-10-15: EMS 알람 **정의** 기반 매핑(5장) 추가 — 발생 건수·선행성은 미검증.
> EMS 알람 코드(알람명 목록·건수)를 받으면 타겟과 RCA 룰을 한 번 더 조정한다.
> 표기: **[확인]** = 코드·문서로 확인한 사실(위치 명시), **[추정]** = 검증하지 않은 판단, **[합의]** = 2026-10-14 사용자 합의(현장 근거 없음), **[미정]** = 현장 답변 필요.

## 1. 왜 타겟을 먼저 정하나

- **[확인]** 지금까지의 성능 수치(F1, 조기 탐지율, AUPRC, 게이트 판정)는 전부 시뮬레이터 장애 3종(`crc_error`, `optical_degradation`, `traffic_drop` — `validation/simulator/scenario_generator.py:25`) 기준이다. 실제 망에서 어떤 장애를 잡을지는 정해진 적이 없다.
- 타겟이 정해져야 ① 평가 정답(무엇을 양성으로 칠지), ② 합격 기준 C1~C6 의 적용 범위, ③ 필요한 데이터(트래픽/광/알람 이력), ④ 남길 RCA 룰이 정해진다.
- 이에 따라 성능·게이트 관련 Backlog(P1-6b, P1-4, 모델 튜닝, P3, P2-4)는 **보류**하고, 타겟 정의 → RCA 룰 16→7 축소 → P1-2 실데이터 도구 순으로 진행한다 (`handoff_target_first.md` 1장).

## 2. 잠정 타겟 표 [합의]

| 층 | 타겟 | 판정 포함 | 평가 방법 |
|---|---|---|---|
| 예측·탐지 (핵심) | **에러(CRC) 점진 증가** | 포함 | 테스트망 30대 트래픽/에러 성능 + EMS 알람 이력 |
| 탐지 (핵심) | **트래픽 급감·단절** | 포함 | 같음 |
| 관찰용 | 광 열화 (수신 광파워 저하) | **판정 제외** | 광 데이터가 2~3대분뿐이라 통계 평가 불가 → 그래프로 관찰 |
| 제외 | 갑작스러운 HW 고장, 전원 이상, 공격성 트래픽 폭주(스톰·DDoS) | 제외 | 15분 성능 데이터에 선행 징후가 없을 가능성 [추정] |
| 리드타임 | "수 시간 전" (임시값) | — | **1h / 3h / 6h** 로 나눠 보고 |

- **실데이터 계획 [합의]**: 사용자가 테스트망 30대의 트래픽 성능 + 알람 이력을 확보한다. 광은 2~3대분만 가능. EMS 알람 이력 테이블에서 `DISTINCT 알람명 + 건수`(정의 목록보다 실제 발생분)를 받는 것을 우선한다.

## 3. 장애 유형별 정의 (4항목)

### 3.1 에러(CRC) 점진 증가 — 핵심

| 항목 | 내용 |
|---|---|
| 어떤 장애 | 포트의 `error_packet`(CRC/FCS 등)이 수 시간에 걸쳐 증가하다가 통신 품질 저하·링크 장애로 이어지는 경우. 원인 후보: 커넥터 오염, SFP 열화, 케이블 차폐 불량 [추정] |
| 사전 징후 | **있을 것으로 가정** [추정]: 장애 전에 에러 카운터가 0 이 아닌 값으로 늘어나는 구간. 실제 망에서 징후 구간이 얼마나 긴지, 정상에서도 산발 에러가 얼마나 나는지는 **모름** [미정] |
| 필요 리드타임 | "수 시간 전" 임시값 [합의] → 1h/3h/6h 분할 보고. 현장 필요값은 [미정] (질문 Q3) |
| 정답 기록처 | EMS 알람 이력(CRC 임계 초과·Link Down 등 해당 알람명은 [미정], 질문 Q1), 장애 티켓·조치 이력, 현장 검토 라벨(`report_package.md` 4.3 의 유효-장애/유효-예방) |

- **[확인] 시뮬레이터와의 관계**: 시뮬레이터 `crc_error` 는 3~8시간(12~32스텝) 램프에서 에러가 `magnitude × 진행도²` 로 늘고(30~5000건, log-uniform) 트래픽이 최대 20% 줄어든 뒤 1~6시간 지속된다(`scenario_generator.py:42-43`, `:146-149`). 실제 증가 곡선·크기는 확인된 적 없다.
- **[확인] 관련 룰(남길 7개 중)**: TR-006(에러 점진 증가, `min_error_packet_trend_slope 0.1`), TR-004(에러 폭주, `min_error_packet_ratio 2.0`) — `src/rca/rules/default_rules.json`. 임계값 근거 기록은 없음.

### 3.2 트래픽 급감·단절 — 핵심

| 항목 | 내용 |
|---|---|
| 어떤 장애 | 포트의 수신/송신 패킷이 평소 대비 급격히 줄거나 0 이 되는 경우(링크 단절, 상위 경로 문제, 논리적 차단 등) [추정: 원인 구분은 15분 카운터로 어려움] |
| 사전 징후 | **대부분 없을 것** [추정]: 단절은 순간 사건인 경우가 많아 "예측"보다 "빠른 탐지"가 목표. 다만 점진 감소형(업스트림 문제 등)이 실제로 있는지는 [미정] |
| 필요 리드타임 | 급감·단절은 **탐지 지연**(발생 후 몇 스텝 안에 알람)으로 본다 [추정]. 점진형이 확인되면 1h/3h/6h 리드타임도 보고 |
| 정답 기록처 | EMS Link Down / 포트 Down 계열 알람(정확한 알람명 [미정]), 계획 작업 이력(작업에 의한 정상 단절을 구분하기 위해 필수, 질문 Q5), 장애 티켓 |

- **[확인] 시뮬레이터와의 차이 (주의)**: 시뮬레이터 `traffic_drop` 은 **3~8시간에 걸친 점진 감소**(50~95% 감소, `scenario_generator.py:44`, `:153-156`)이며 순간 단절은 없다. 즉 이번 타겟 "급감·단절"은 시뮬레이터 장애와 **형태가 다르다**. 그동안의 traffic_drop 성능 수치(P1-4 의 취약점 포함)는 이 타겟의 근거가 되지 못한다.
- **[확인] 계획 작업과의 구분**: 정상적인 작업 단절은 현장 검토 분류상 "정상 변동"(무효)이며(`report_package.md` 4.3), C6 의 망 이벤트일 기록과도 연결된다.
- **[확인] 관련 룰**: TR-003(수신 단절, `max_rx_packet 0`), TR-005(수신 급감, `max_rx_packet_ratio 0.5`).

### 3.3 광 열화 — 관찰용, 판정 제외

| 항목 | 내용 |
|---|---|
| 어떤 장애 | 수신 광파워(`rx_avg_power`)의 점진 저하(커넥터 오염 등) 또는 급격한 저하(패치코드 꺾임)가 LOS 로 이어지는 경우 [추정] |
| 사전 징후 | 점진 저하형은 있을 것 [추정]. 신호가 단순해 AE 없이 규칙(기준선 대비 dB 하락)으로 충분할 수 있다 [추정, `handoff_target_first.md` 2장] |
| 필요 리드타임 | 판정하지 않음. 관찰 시 1h/3h/6h 참고 표시 |
| 정답 기록처 | EMS LOS / 광 레벨 임계 알람(알람명 [미정]). 단 대상 장비 2~3대라 이벤트가 거의 없을 것 [추정] |

- **판정 제외 사유 [합의]**: 광 데이터 2~3대분으로는 C2(샘플 ≥ 100)·C3(이벤트 ≥ 20) 같은 통계 판정이 불가능하다. 그래프로만 관찰한다.
- **[확인] 관련 룰**: OP-001(LOS, `max_rx_avg_power -24`), OP-003(급격 저하, slope -1.0), OP-006(점진 저하, slope -0.1). 임계값 근거 기록 없음.

### 3.4 제외 유형

| 유형 | 제외 이유 |
|---|---|
| 갑작스러운 HW 고장, 전원 이상 | 15분 성능 카운터에 선행 징후가 없을 가능성 [추정]. 발생 후에는 단절(3.2)로 잡힐 수 있으나 "예측" 대상은 아님 |
| 공격성 폭주(스톰·DDoS) | 15분 카운터만으로 원인 구분이 어렵다 [추정]. 관련 룰 TR-001·TR-002 는 보관으로 이동 합의(`handoff_target_first.md` 4장) |

- 제외 유형도 **EMS 알람 이력에는 섞여 들어온다**. 약한 정답(C3) 계산 시 이들을 분모에 넣으면 선행 탐지율 상한이 낮아지므로, 어떤 알람명을 분모에 넣을지는 5장 매핑(정의 기반 잠정)과 Q1-1~Q1-3 답변 후 정한다 [미정].

## 4. AE(오토인코더)의 위치

- **광 AE**: 폐기하지 않고 **"실험적, 판정 제외"** 로 내린다 [합의]. 코드·모델·레지스트리는 그대로 두고, 광 트랙 결과는 섀도 판정(C1~C6)에서 집계하지 않는다(관찰용 그래프만).
- **트래픽 AE도 확정이 아니다**: [확인] 시뮬레이션에서 롤링 규칙 베이스라인(`validation/evaluation/baselines.py:27` — 직전 24h 중앙값 대비, 에러 ≥ 20 / 광 3dB 하락 / 트래픽 15% 미만)이 이벤트 F1 0.919·오탐 0.003 으로 AE(v2+오탐 억제형 F1 0.760, `docs/design/p1_3_model_promotion.md` V4)보다 높다. 단 롤링 규칙의 임계값이 시뮬레이터 장애에 맞춰져 있을 가능성이 높아 [추정] 실데이터 성능으로 해석할 수 없다.
- **결론**: AE 를 유지·축소·폐기할지, 규칙 + AE 하이브리드로 둘지는 **실데이터에서 AE·고정 임계치·롤링 규칙을 같은 기간·같은 포트로 비교한 결과로 결정**한다(P1-2 `real_data_check` 의 오프라인 재생 기능, `report_package.md` 6.2). 그 전에는 AE 성능 튜닝을 하지 않는다.

## 5. EMS 알람 정의 기반 타겟 유형 매핑 (2026-10-15)

### 5.1 입력과 한계

- **입력**: 사용자가 제공한 EMS 알람 **정의** 테이블 — 장비 모델별 C 배열 `lpsztbl_<모델>_ALM_RSN`(인덱스 0~255 → 알람명 문자열). 대상 모델: CE8300, CE8600, CE841P, CE7200, CE7300, CE730M, CE7080, CE7700Q/Q2/Q2V, CE7510Q, CE7700, CE73K0, CE7400, CE740C, CE74C2, CE740E, CE7533, CE7534, CE7510, CE7511, CE7610, CE7611, CE5100, CE5200, CE7515.
- **출처 한정**: architect 는 원문을 보지 못했고, lead 가 추린 후보 목록(2026-10-15 전달)을 기준으로 작성했다. 아래 표의 **[확인]** 은 "lead 가 정의 테이블에 그 이름이 있다고 전달함"이라는 뜻이며, 모델 공통 여부는 확인하지 않았다(ETH-ERR 만 "전 모델"로 전달됨).
- **현장 발생 이력은 확보하지 못함** → 정의만으로 진행하기로 사용자가 결정. 따라서 이 매핑으로는 다음을 **검증할 수 없다**:
  - **발생 건수**: 어떤 알람이 실제로 자주 나는지, C3 의 이벤트 ≥ 20 을 채울 수 있는지
  - **선행성**: 알람이 성능 데이터 이상보다 먼저/나중에 나는지(리드타임)
  - **의미·조건**: 정의에는 이름만 있고 **임계값·발생 조건·심각도가 없다**. 알람이 타겟 신호(에러 증가, 트래픽 단절)를 실제로 반영하는지는 이름에서 미루어 본 **[추정]** 이다.
- **매핑 규칙**:
  1. **인덱스가 아니라 알람명으로 매핑**한다. 같은 인덱스가 모델마다 다른 이름이다(예: 195/196 번이 CE8300 계열은 PORT-CFM/PORT-DROP, CE7700 계열은 LINK-LOC/ETH-OV). P1-2 의 EMS 이력 입력도 `(모델, 인덱스)` 가 아니라 알람명 문자열을 키로 받아야 한다.
  2. **RMON-ALARM 은 상승/하강이 같은 이름**이라 방향을 구분할 수 없다 → 타겟 정답으로 쓰지 않는다.
  3. 한 알람이 두 유형에 걸리면(예: OPT-LOS) 표에 모두 적고 용도를 구분한다.

### 5.2 매핑표

타겟 유형: **CRC증가** / **트래픽단절** / **광관찰**(판정 제외) / **제외**(HW·전원·시스템) / **해당없음**(포트 이더넷 타겟과 다른 계층·보조 신호).
"정답 후보 등급"은 약한 정답(C3)으로 쓸 우선순위 [추정]: **1차** = 포트 이더넷 신호와 직접 대응할 것으로 보임, **보조** = 관련은 있으나 계층·원인이 다름, **사용 안 함**.

### 5.3 이 매핑의 용도와 주의

- **약한 정답 후보(C3)**: 1차 등급만 우선 사용 [추정]. CRC증가 = ETH-ERR(+CLI-FCS-SD), 트래픽단절 = ETH-NO-RX/TX-TRAFFIC, ETH-LINK-FAIL, CLI-LINK-*, OTU-ETH-*, OPT-LOS/CLI-OPT-LOS.
- **정상 단절 구분 후보**: LINK-FAIL-MANUAL, BOOTING, RESET, SW-UPDATED, OPT-REMOVE 등 작업성 알람은 계획 작업 이력(Q5)이 없을 때의 대용 근거가 될 수 있다 [추정].
- **순환 위험** [추정]: ETH-ERR 의 임계가 우리 규칙(롤링 규칙 에러 ≥ 20, TR-004)과 비슷하면 "AI 가 ETH-ERR 보다 먼저 울림"이 사실상 같은 카운터의 같은 조건 비교가 된다. 임계 조건(Q1-3)을 알기 전에는 C3 해석을 보류한다.
- **단절은 선행 탐지 대상이 아닐 수 있다** [추정]: ETH-NO-RX-TRAFFIC·LINK-FAIL 은 단절 그 자체를 알리므로 C3(이전 24h~15분 선행)로는 낮게 나올 것. 단절은 탐지 지연 비교로 보는 편이 맞을 수 있다(3.2).

### 5.4 RCA 룰 7개와 알람 대응 가능성 (룰 변경 없음)

> 룰은 바꾸지 않는다(dev 가 7개 축소를 컨테이너 검증 중). 아래는 각 룰의 진단이 어떤 EMS 알람과 같은 현상을 가리킬 수 있는지에 대한 **[추정]** 이며, 룰 조건(`src/rca/rules/default_rules.json`)은 [확인].

| 룰 | 룰 조건 [확인] | 대응 가능 알람 [추정] | 비고 |
|---|---|---|---|
| TR-003 수신 단절 | `max_rx_packet 0` | ETH-NO-RX-TRAFFIC, ETH-LINK-FAIL, CLI-LINK-FAIL, OTU-ETH-LINKDOWN | 가장 직접적. 다만 룰 진단문 "물리 연결은 정상이나 논리적 단절(블랙홀)"은 LINK-FAIL 류(물리 단절)와 원인이 다름 → 같은 현상(rx=0)에 원인을 단정하는 문구 점검 필요 |
| TR-004 에러 폭주 | `min_error_packet_ratio 2.0` | ETH-ERR, CLI-FCS-SD | ETH-ERR 임계 조건과 비교 필요(Q1-3) |
| TR-005 수신 급감 | `max_rx_packet_ratio 0.5`, `min_rx_packet 1` | **직접 대응 알람 없음** (ETH-NO-RX-TRAFFIC 은 '없음'일 것으로 추정) | 0 이 아닌 급감은 EMS 가 알람하지 않을 수 있음 → 정답 기록처가 없을 가능성. 현장 검토 라벨로만 평가 |
| TR-006 에러 점진 증가 | `min_error_packet_trend_slope 0.1` | ETH-ERR 의 **선행** 단계, CLI-CV-SD·CLI-FCS-SD(SD = 열화 단계) | 예지 타겟의 핵심 룰. ETH-ERR 이 나기 전 구간을 잡는지가 C3 의 주제 |
| OP-001 LOS | `max_rx_avg_power -24` | OPT-LOS, CLI-OPT-LOS, OTU-LOS | 광관찰(판정 제외). OPT-LOS 는 단절 정답으로도 쓰임 |
| OP-003 광 급격 저하 | `max_rx_avg_power_trend_slope -1.0` | OPT-PWR-LOW 계열(속도 구분 불가) | 관찰용 |
| OP-006 광 점진 저하 | `max_rx_avg_power_trend_slope -0.1` | OPT-PWR-LOW-1~4 / LO-PWR1~4(단계 임계일 경우), OPTIC_PRE_BER | 관찰용 |

- 매핑에서 보면, 보관 예정 9개 중 다시 살릴 근거가 될 알람은 이번 정의 목록만으로는 보이지 않는다 [추정] — 단 건수가 없어 단정하지 않는다.

## 6. 현장 질문지 (팀장·현장 담당자용)

### A. 알람·장애 이력
- **Q1. [정의 확보됨 2026-10-15, 발생 건수는 미확보]** 알람 정의(모델별 `lpsztbl_<모델>_ALM_RSN`)는 받았고 5장에 매핑했다. 남은 질문:
  - **Q1-1.** 실제 발생분(알람명별 건수, 발생/해제 시각)은 EMS 이력 접근이 가능해진 뒤 받을 수 있나요? (예: `SELECT 알람명, COUNT(*) ... GROUP BY 알람명`, 가능하면 최근 6개월 이상) 이력에 장비 IP·포트(cid/lid) 식별자가 있나요?
  - **Q1-2.** 테스트망 30대의 장비 모델은 위 목록(CE8300 … CE7515) 중 어느 것인가요? (모델마다 알람 이름 체계가 달라 쓸 수 있는 정답 알람이 달라짐 — 예: CLI-* 는 7700 계열, OTU-ETH-* 는 8600·841P)

  - **Q1-4.** RMON-ALARM 은 어떤 카운터에 설정되어 있나요? (상승/하강이 같은 이름이라 지금은 정답으로 쓰지 않음)
- **Q2.** 운영자가 "미리 알았으면 좋았을" 장애는 주로 어떤 유형인가요? 에러 점진 증가, 트래픽 급감·단절 외에 중요한 유형이 있나요?
