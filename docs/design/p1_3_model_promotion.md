## 0. 요약 (확정)
| 범위 | 결정 |
|---|---|
| **A. v2 승격** (D1=A2) | 실험 모델 파일을 복사하지 않는다. **P1-1 운영 학습 파이프라인으로 v2 를 새로 학습**하고, 학습 설정은 실험 레시피 **30에폭·배치 64·인내 5** 로 지정한다. v1 은 레지스트리에 남겨 롤백용으로 쓴다 |
| **B. 알람 정책** (D2, D3=B3) | 오탐 억제형(precision) 정책을 **임시 채택**하되 **v2 와 짝으로만** 적용한다. 방식은 **모델별 정책**: 모델 메타데이터에 `alert_policy` 를 저장하고, 롤백하면 정책도 함께 돌아간다. 정책 메타가 없는 모델(v1)은 지금의 기본 정책으로 동작한다(골든 테스트 유지). 실데이터 섀도에서 재확인한다(4.4) |
| **C. G3 판정** (D4→D-b=C4') | **절대 상한(전체 인시던트 0.05) 위반은 WARN**(정보 + auto 차단), **상대 기준(후보 ≤ max(활성 × 1.5, 0.01)) 위반은 FAIL 유지**. 처음 결정한 C3(추정 오탐 기준)는 U3b 결과로 폐기(5장, 12장) |
| D5 | `MODEL_CONFIG` 기본 학습 설정(100/32/10) 변경은 **범위 밖** |

**진행 순서: B(정책 메커니즘) → V1·V2(정책 확정) → C(G3 C4' 구현, V3) → A(v2 학습·승격).** 한 단계에 한 가지만 바꾸고(lessons #29), 선택은 개발 시드로, 확인은 검증 전용 시드로만 한다(#30). 승격 게이트와 수동 롤백은 그대로 쓴다(#28).

## 1. 배경과 범위
plan.md P1-3: "실험 모델 승격(v2): 정상 구간 정제를 학습 파이프라인에 포함, v1 은 롤백용 보존 + 게이트 G3 절대 상한(0.05) 보정". 여기에 P0-2 의 남은 과제(정책 프리셋 적용 결정, `performance_report.md` 6장 2)와 report_package 6.1 의 "정책 우선순위 = 오탐 억제형(임시 확정)" 이 묶인다.

현재 운영 상태(사실):
- 활성 모델은 두 트랙 모두 **v1** (오염된 학습 데이터 + 스케일러 버그로 학습, 시뮬레이션 이벤트 F1 0.325, `performance_report.md` 2장). 메타에 `baseline_port_median` 이 없는 legacy 라 드리프트 재학습이 notify 로 막혀 있다.
- 알람 정책은 **기본(default)** — `src/pipeline/alerting.py` `AlertPolicy` 기본값. 정책은 프로세스 시작 시 `config.ALERT_POLICY` 로 한 번 읽는 **전역값**이다(`alerting.load_policy`, `AnomalyDetector.__init__`).
- 게이트 G3 절대 상한 0.05 는 장애를 포함한 전체 인시던트 기준이라 정상 후보도 FAIL 한 사례가 있다(광 0.063, traffic 0.051·0.072; P1-1 설계서 8장).

### 2.2 격리 재학습 실험 모델의 산출물과 재현
- **원래 실험 모델(GEMINI.md "격리 재학습 실험", `validation/runs/models_noisy` 등) 파일은 이 환경의 어느 체크아웃에도 없다**(`validation/runs/` 는 git 제외). 확인한 곳: main 체크아웃, `ptn-wt/architect`, `ptn-wt/dev`.
- 가장 가까운 산출물(git 제외): `ptn-wt/dev/validation/runs/excl_{truth,auto,none}_s{101,103}` — P1-1 D, **두 트랙**, 30/64/5, 시뮬레이션 시드 101·103, 메타에 `baseline_port_*` 있음.
- 재현(코드는 git 에 있음): 실험 모델 `validation/cli/train_isolated.py --variant noisy --seed 101 --epochs 30 --out …`, 정제 비교 `validation/cli/compare_train_exclusion.py train/eval`, 정책 평가 `validate_policy.py`·`sensitivity.py`.
- 실험 모델은 **시뮬레이터 데이터로 학습**했다. 그래서 D1 에서 파일 승격(A1)을 하지 않기로 했다.

### 2.3 v2 승격이 legacy 기준값 차단을 해소하는가
- **해소된다 — 현재 Trainer 로 학습한 모델을 트랙별로 승격할 때.** `retrain_policy.decide()` 는 활성 모델 메타에 `baseline_port_median` 이 없으면 notify 만 한다. 현재 Trainer 는 이 값을 기록한다(`src/models/trainer.py`). P1-1 traffic 컨테이너 확인에서 force 승격한 v2 의 `baseline_legacy=False` 확인됨.
- 두 트랙을 모두 승격해야 두 트랙 모두 해소된다. 승격 직후 24h 는 `warming_up`(정상).

### 2.4 설계에 영향을 주는 사실
1. **G2 는 traffic v2 승격에서 FAIL 이 예상된다.** v1 traffic 검증 손실 3.01, P1-1 실험 모델 약 0.043~0.044 → 약 1/68 배로 3배 기준 밖. 활성 모델이 비정상이라 생기는 의도된 FAIL(P1-1 설계서 2.6, lessons #34). 광은 v1 0.0175·임계치 0.170 대 실험 0.0245·0.264 로 기준 안.
2. **G4 는 카나리 파일이 없으면 SKIP** 이다. 승격 전 `validation/cli/build_canary.py` 로 `<ft>_canary.csv` 를 모델 볼륨에 둔다.
3. **G3 는 정책에 따라 값이 달라진다.** 오탐 억제형에서는 알람 인시던트가 크게 줄어(시뮬레이션 오탐 0.100 → 0.010) 지금의 G3 FAIL 이 정책만으로 해소될 수 있다 → C 는 B 이후에 측정.
4. 운영 DB(`cowptn_test`)에는 현재 **시뮬레이션 시드 데이터만** 있다(GEMINI.md P1-1 항목). 따라서 이 환경에서 운영 파이프라인으로 학습한 v2 도 **실질적으로 시뮬레이터 데이터로 학습한 모델**이다.

## 3. A — v2 승격 (D1 = A2 확정)
- 학습 경로: 운영 파이프라인 `/api/model/train` (P1-1: 포트 홀드아웃, 의심 구간 제외 A∪B∪C, 게이트 자동 실행, 후보 저장).
- 학습 설정: `training_config={"epochs": 30, "batch_size": 64, "patience": 5}` 를 요청에 명시. 그 외 아키텍처는 v1 과 동일. 근거: 오탐 억제형 정책의 짝(`performance_report.md` 3·5장, lessons #29).
- 학습 설정 재사용: v2 가 활성화되면 이후 드리프트 재학습은 v2 의 저장 설정(30/64/5)을 자동으로 이어받는다 → **코드 변경 없음**. `MODEL_CONFIG` 기본값 변경은 범위 밖(D5).
- 정책 지정: 학습 요청에 `alert_policy="precision"` (4장, U1 에서 추가). 메타에 기록되고 게이트가 그 정책으로 후보를 평가한다.
- 두 트랙 모두 학습·승격(레지스트리가 트랙별이라 따로 승격 가능). v1 은 삭제하지 않는다.

## 4. B — 모델별 알람 정책 (D2·D3 확정)

### 4.1 결정 내용
- 오탐 억제형(precision: `threshold_scale=3.0, sigma_k=2.0, dampening_steps={1:6, 2:4, 3:3}`)을 **임시 채택**, **v2 와 짝으로만** 적용. v1 에는 적용하지 않는다.

| 지표 (검증 전용 시드 3개, noisy 모델, 시뮬레이션) | 기본 정책 | 오탐 억제형 |
|---|---|---|
| 이벤트 F1 | 0.617 ± 0.024 | **0.796 ± 0.011** |
| 오탐/포트·일 | 0.100 ± 0.007 | **0.010 ± 0.002** |
| 이벤트 정밀도 | 50.0% | 90.2% |
| 조기 탐지율 | **77.2%** | 65.3% |
| 리드타임 중앙값 | **205분** | 152분 |
| 최소 알람 지연 (CRITICAL) | 1스텝(15분) | 3스텝(45분) |

- **받아들인 대가**: 조기 탐지 약 12%p 감소, 리드타임 약 50분 단축, 약한 장애 조건 조기 탐지 29.6%(`performance_report.md` 4장).
- **운영 레시피 결과(V2, 2026-10-06)**: 위 표는 실험 레시피 모델 기준이다. 운영 레시피로 학습한 모델에서는 오탐 0.029·조기 탐지 68.1%·F1 0.760 으로 **V2 FAIL**(C1 0.02 미달). 사용자 결정 A 로 임시 채택 유지, 섀도에서 재확인(6장 V1·V2 결과).

### 4.2 동작 규칙 (B3)
1. 정책 결정 순서(트랙별): **활성 모델 메타의 `alert_policy`** → 없으면 `config.ALERT_POLICY` → 없으면 `AlertPolicy()` 코드 기본값. v1 은 메타에 정책이 없으므로 지금과 똑같이 동작한다(골든 테스트 불변).
2. 메타 형식: 프리셋 이름과 **`AlertPolicy` 의 5개 필드 전부**(`sigma_k`, `dyn_cap`, `threshold_scale`, `severity_decay`, `dampening_steps`)를 실제 값으로 저장한다(2026-10-06 구현 반영, `alerting.policy_to_meta`). 예: `"alert_policy": {"preset": "precision", "sigma_k": 2.0, "dyn_cap": 1.2, "threshold_scale": 3.0, "severity_decay": 0.5, "dampening_steps": {"1": 6, "2": 4, "3": 3}}`. 프리셋 정의가 나중에 바뀌어도 그 모델의 정책은 고정된다. 값이 프리셋과 일치하지 않으면 `preset="custom"`.
   - 복원(`alerting.policy_from_meta`): 메타가 없거나 비면 `None`(= 정책 미지정 → 4.2-1 우선순위). 일부 필드가 빠져 있으면 **그 프리셋(없으면 코드 기본값)의 값으로 보충**한다. `dampening_steps` 키는 문자열(`"1"`)이어도 복원.
3. 추론기(`AnomalyDetector`)는 정책을 **트랙별로** 보관하고, `reload_model(ft, version)` 때 그 버전 메타의 정책으로 바꾼다. Consumer 는 이미 Redis `reload` 로 리로드하므로 승격·롤백 시 정책도 함께 바뀐다(재시작 불필요).
4. 학습 시 지정: `/api/model/train` 에 `alert_policy`(프리셋 이름, 선택). 지정하지 않으면 **활성 모델의 정책을 이어받는다**(드리프트 재학습 포함, 학습 설정 재사용과 같은 방식). 활성 모델에도 없으면 메타에 기록하지 않는다(= 기본 정책).
5. **정책만 바꾼 새 버전**: 같은 가중치로 정책만 바꿔야 할 때(섀도 결과 반영 등, 4.4) 재학습하지 않고 `POST /api/model/policy?ft&version&preset` 로 **새 후보 버전**(가중치·스케일러 파일은 원 버전 참조, 메타의 `alert_policy` 만 다름, `derived_from` 기록)을 만든다. 한 번에 한 가지(정책만) 바꾸는 경로이고, 레지스트리 이력·롤백이 그대로 적용된다.
   - 확정(2026-10-06, 구현 반영): 새 버전의 `trigger` 는 **`policy`**, `trained_at` 은 **원 버전의 값을 유지**(가중치를 학습한 시점이므로). 이 API 는 게이트를 **동기로 실행**하고 생성된 버전과 게이트 결과를 함께 반환한다.
   - **UI 에는 정책 전용 버전 만들기 버튼이 없다(이번 범위 밖).** API 로만 만든다. UI 는 버전 목록에서 정책과 `trigger=policy` 를 표시만 한다.
6. 게이트(G3)는 **후보는 후보 정책으로, 활성은 활성 정책으로** 알람을 계산한다(= 운영에서 실제로 날 알람의 비교). 게이트 `data` 에 두 정책을 기록한다.

### 4.3 트랙 간 정책
정책은 두 트랙 결합 결과로 선택했다(`tune_alerting.py`). B3 는 트랙별 저장이지만 v2 는 **두 트랙 모두 precision** 으로 시작한다(트랙별로 다른 정책을 의도적으로 쓰는 것은 근거 데이터가 없어 범위 밖).

**두 트랙의 정책이 다를 때(확정 2026-10-06)** — 트랙을 따로 승격·롤백하면 일시적으로 생긴다(예: traffic=v2+precision, optical=v1+기본).
- 트랙별 단계(동적 임계치 `sigma_k`·`dyn_cap`·`threshold_scale`, 심각도 `severity_decay`)는 **각 트랙의 정책**을 쓴다.
- 포트의 결합 등급에 적용하는 **댐프닝(연속 횟수)은 우세 트랙의 정책**을 쓴다. 우세 트랙 규칙은 통합 지표와 같다(`get_dominant_metrics`: traffic 심각도 ≥ optical 심각도이면 traffic, 같으면 traffic). 구현: `src/pipeline/inference.py` `apply_dampening`.
- 근거: 결합 등급 자체가 우세 트랙의 심각도에서 나오므로(lessons #10), 그 등급을 만든 모델과 짝인 정책으로 거르는 것이 정책-모델 짝 원칙과 맞다. 우세 트랙이 스텝마다 바뀌면 같은 연속 카운트에 다른 요구 횟수가 적용될 수 있으나, 혼합 상태는 트랙별 승격 사이의 과도기에만 생긴다.
- 검토한 대안: (a) 두 정책 중 **더 엄격한 쪽**(등급별 요구 횟수의 최댓값) — 기본 정책 모델의 알람까지 오탐 억제형 기준으로 늦춰 그 모델의 검증된 동작과 달라짐, (b) **트랙별 댐프닝 상태를 따로** 두고 결합 — 상태 구조와 기존 골든·동등성 테스트를 바꿔야 해 범위가 큼. 둘 다 채택하지 않음.
- 두 트랙의 정책이 같으면(v1+v1, v2+v2) 이 규칙은 결과에 영향이 없다.

### 4.4 실데이터 섀도에서의 재확인과 재조정 (report_package 6.1 과의 정합)
정책 수치는 시뮬레이션이므로 **실데이터 섀도 운영에서 재확인**한다. 섀도 운영 절차(`docs/report_package.md` 5장)와 다음과 같이 맞춘다.

| 대상 | 바꿀 수 있는 시점 | 근거 |
|---|---|---|
| **합격 기준 값** (C1 상한, C2 목표) | **섀도 시작 전에만**. 섀도 시작 후 동결 | report_package 6.1 조정 규칙 (변경 없음) |
| **모델·정책** (v2 + precision) | 섀도 **개발 기간(1~2주차)** 에는 정책 재선택 허용. **판정 기간 시작 시 동결**하고, 판정 기간 중 바꾸면 판정 기간을 처음부터 다시 시작 | report_package 5.3 |
| **섀도 판정 결과로 정책을 바꿀 때** (4.4 "조건부" 등) | 정책 변경은 **새 버전**(4.2-5)으로 만들고 **별도의 새 판정 기간**으로 평가한다. 같은 판정 기간 데이터로 고르고 다시 판정하지 않는다 | report_package 4.4, lessons #30 |

- 원칙 문구(설계·보고에 그대로 사용): **"합격 기준은 섀도 시작 전에, 모델·정책은 판정 기간 시작 전에 동결한다. 섀도 결과로 정책을 바꾸면 그것은 새 후보이며, 새 판정 기간으로만 평가한다."**
- 재조정 절차:
  1. 섀도 판정 결과가 "조건부"(C1 초과이고 정책 조정으로 해결 가능 등) 또는 운영 측 요청.
  2. **개발 기간 데이터**(판정 기간 데이터가 아님)로 대안 정책(프리셋 2종 + 임계치 배율 격자, report_package 4.4 와 같은 후보군)을 오프라인 재생해 고른다.
  3. 고른 정책으로 4.2-5 의 **정책 전용 새 버전**을 만들고 게이트를 돌린다.
  4. 승격 후 **새 판정 기간**(report_package 5.3 의 판정 기간 규칙)으로 평가한다.
- 기본 정책으로 되돌리는 것(D2 철회)도 같은 절차다: 정책 메타가 없는(또는 `preset=default`) 새 버전 또는 v1 롤백.

## 5. C — 게이트 G3 판정 (D4 = C3 → **D-b = C4' 로 변경**, 2026-10-06)

### 5.1 문제
G3 = 홀드아웃 포트 × 최근 3일의 알람 인시던트/포트·일. 기존(P1-1) PASS 조건은 `cand ≤ max(active × 1.5, 0.01)` **그리고** `cand ≤ 0.05`. 실제 장애에 대한 정당한 알람도 포함하므로 장애가 많은 데이터에서는 좋은 모델도 절대 상한을 넘는다(광 0.063, traffic 0.051·0.072 FAIL / 0.042 PASS). 원래 의도는 "C1(오탐 ≤ 0.02)과 맞춘 알람 부하 상한" 이었다(P1-1 설계서 2.6).

### 5.2 U3b 측정 결과 (개발 시드 7·11, 학습 시드 101·103, 2026-10-06, dev 로그 `ptn-wt/dev/validation/runs/p1_3/logs/u3b_*.log` — git 제외)

### 5.3 판정 규칙 (C4', 확정)
트랙별로, 최소 포트·일 가드(150 미만 → SKIP → 종합 WARN)를 먼저 적용한 뒤:
1. **상대 기준** (활성 모델이 있을 때): `cand_total > max(active_total × gate_max_alarm_ratio(1.5), gate_alarm_floor(0.01))` → **FAIL** ("활성 모델 대비 과다").
2. **절대 상한**: 상대 기준을 통과했거나 활성 모델이 없을 때 `cand_total > gate_max_incidents_per_port_day(0.05)` → **WARN** ("절대 상한 초과 — 장애가 많은 기간일 수 있음, 사람이 검토").
3. 그 외 → PASS.
- 종합 규칙은 기존 그대로(FAIL > WARN > PASS, G3 SKIP 은 종합 WARN). **auto 는 PASS 에서만 승격**하므로 절대 상한 초과 후보는 자동 승격되지 않는다. 수동 승격은 WARN 이라 `force` 없이 진행되고 경고가 `warnings` 로 반환된다(P1-1 2.7).
- 값·한도 표기: 상대 기준 FAIL 이면 `value`=후보 비율, `limit`=상대 상한. 절대 상한 WARN 이면 `value`=후보 비율, `limit`=0.05. `detail`(인시던트 수·포트·일)은 P1-1 형식 그대로.
- 설정 키는 그대로 쓴다(`gate_max_incidents_per_port_day` 의 의미만 "FAIL 상한" → "WARN 상한" 으로 바뀜). 새 키 없음.
- 이 규칙은 P1-1 설계서 2.6 G3 행의 판정(절대 상한 위반 = FAIL)을 **대체**한다.

### 5.4 한계 (C4')
- **첫 승격(활성 = v1 + 기본)에서는 G3 가 사실상 정보용**이다: 상대 기준은 v1 의 과다 알람 때문에 판별력이 없고, 절대 상한은 WARN 이라 수동 승격을 막지 않는다. → **V1~V4 오프라인 검증, G4 카나리(SKIP 아님), 사람 검토**로 보완한다.
- **재학습 래칫 위험**: 상대 기준(1.5배)은 재학습마다 알람량이 조금씩 오르는 것을 막지 못한다(최악 1.5^k). → **G5(임계치 상승 추세 경고)** 와 섀도 운영의 **C1(추정 오탐 부하)·C6(알람량 안정성)** 으로 감시한다.
- **traffic_drop 위주 환경에서는 게이트가 판별하지 못한다**(정상·과다 모두 알람이 거의 없음). 점진적 트래픽 감소 탐지 자체의 약점(`performance_report.md` 4장)과 같은 원인이며 **P1-4 로 이월**한다(D-c).
- 절대 상한 0.05 는 이제 하드 차단이 아니므로, 장애가 잦은 기간에 정상 후보도 WARN 이 되어 auto 승격이 보류된다(의도된 보수성: 대규모 장애 중 재학습을 피하는 P1-1 원칙과 같은 방향).

### 5.5 폐기한 C3 (기록)
처음 결정(D4)은 C3(규칙 B 의심 구간 밖 인시던트에 절대 상한 0.05)였으나, U3b 에서 optical 잦음 조건의 정상 후보를 FAIL 시키고(규칙 B 커버리지 한계) 구현(U4)이 필요해 **사용자 결정으로 폐기**했다(2026-10-06). `validation/cli/check_promotion.py` 의 `fp_incidents_per_port_day`·`c3_status` 는 V3 의 참고 열로만 남긴다(운영 판정에 쓰지 않음).

**V3 세부 (2026-10-06 재정의, D-a)**

> **변경 기록**: 2026-10-06 U3b(개발 시드 7·11)에서 사전 고정한 과다 후보(임계치 ×0.5)가 실제로 과다하지 않음(precision 의 threshold_scale 3.0 과 동적 임계치 때문)을 확인하고 정의를 속성 기준으로 바꿈. 바꾼 기준은 개발 시드 결과를 본 뒤 정했으므로 개발 시드 판정은 탐색으로만 표시하고, 근거는 미개봉 검증 시드 23·31·47 1회 판정만 씀. 그 결과로 기준·식을 다시 고르지 않음.

- **실행 순서**: V3 는 **V2 결과와 사용자의 정책 확정 이후**에 실행한다. 후보 풀의 "precision" 은 V2 에서 확정된 **최종 정책**이어야 한다(V2 에서 정책을 다시 고르면 그 정책).
- **게이트 데이터**: 학습·평가와 다른 시드(탐색용 **7·11**, 근거용 **23·31·47**)로 **60포트 × 4일**(규칙 B 기준선 1일 + 판정 3일, 180포트·일 ≥ 150). 시뮬레이션 데이터는 학습과 독립이므로 전 포트를 홀드아웃으로 본다. 장애 밀도 2종: 기준(평균 7일 간격), 잦음(평균 2일 간격).
- **판정 라벨 (속성 기준, 게이트 식과 독립)** — *2026-10-06 2차 재정의(V2 결과 반영, 12장)*: 각 후보의 **truth-FP** = 시뮬레이터 정답 에피소드와 겹치지 않는 알람 인시던트/포트·일(정답은 검증에서만 쓰며 게이트는 쓰지 않음). 기준은 **같은 게이트 데이터에서 잰 후보 ①(사용자가 임시 채택한 운영 구성 = V1 모델 + 확정 정책)의 truth-FP(이하 F①)** 에 둔다.
  - **정상** = 후보 ① (정의상 기준 구성), 그리고 truth-FP ≤ F① 인 후보
  - **과다** = truth-FP ≥ **max(3 × F①, 0.04)**
  - **중간** = 그 외 → **판정에서 제외**하고 값만 기록
  - **F① 의 측정 단위**(확정 2026-10-06, V3 도구 구현 반영): **시드 × 밀도 × 트랙별로 같은 게이트 데이터**에서 잰다(다른 조건의 F① 을 섞지 않음).
  - **truth-FP 의 정의**(확정): 평가 도구 `validation/evaluation/metrics.event_metrics` 의 false incident 정의를 재사용 — 어떤 에피소드의 활성 구간에도 속하지 않는 알람을 묶은 인시던트. U3·`performance_report.md` 의 오탐 수치와 같은 정의라 일관된다. **한계**: 에피소드를 **트랙 구분 없이** 쓰므로, 한 트랙 후보가 다른 트랙 장애 구간에 낸 알람(그 트랙 입력에는 신호가 없어 사실상 오탐)은 오탐으로 세지 않는다. 카나리의 트랙별 라벨(P1-1 설계서 2.10, lessons #35)과 다르며, 모든 후보에서 같은 방향(과소 계상)이고 장애가 잦은 조건일수록 크다. F① 대비 상대 라벨이라 판정 영향은 작을 것으로 보지만 측정하지 않았다.
  - **라벨이 없는 조건**(확정): 한 조건(시드 × 밀도 × 트랙)에 과다 라벨 후보가 없으면 그 조건의 **과다 기준은 판정 불가**로 기록하고 **정상 기준은 그대로 적용**한다. 과다 라벨 후보가 **전 조건에 하나도 없으면 V3 전체를 판정 불가**로 기록한다(합격으로 보지 않음).
  - 근거(모두 V3 게이트 데이터를 보기 전의 것): 3배 = G2 비율 한도(`registry.THRESHOLD_RATIO_LIMIT`), 0.04 = `report_package.md` 5.6 경보선(F① 이 0 에 가까울 때 작은 차이를 과다로 부르지 않기 위한 하한). 게이트의 상대 기준 1.5배는 **쓰지 않는다**(라벨이 게이트 식을 그대로 따라가지 않도록).
  - 이전 정의(정상 ≤ 0.02 = C1)를 바꾼 이유: 사용자가 임시 채택한 구성의 오탐이 U3 에서 0.029(검증 시드 평균)~0.039(개발 시드 평균)로 C1 을 넘어, 이전 정의로는 **정상 후보가 하나도 없어** V3 가 판정 불가가 됨. 정상의 절대 수준은 V2(FAIL 기록)와 섀도 C1 이 판단하고, V3 는 "확정 구성 대비 과다 알람을 G3 가 가려내는가" 만 본다.
- **후보 풀 (5개 고정, 메커니즘과 무관하게 라벨은 위 속성으로 붙임)**:
  1. V1 모델 + 최종 정책 (**기준 구성 — 정의상 정상**)
  2. V1 모델 + 기본 정책 (정책 짝이 틀린 현실적 사례)
  3. V1 모델 임계치 × 0.25 + 최종 정책
  4. V1 모델 임계치 × 0.1 + 최종 정책
  5. v1 + 기본 정책 (현재 활성)
- **활성 2가지**: (a) **첫 승격** — 활성 = v1 + 기본 정책, (b) **이후 재학습** — 활성 = 정상 v2(① 과 같은 모델) + 최종 정책. 상대 기준은 (b)에서만 판별력이 있다(5.2).
- **합격 기준**:
  - 정상 후보: (a)·(b), 두 밀도, 모든 시드에서 G3 가 **FAIL 이 아님**(PASS 또는 WARN).
  - 과다 후보: (a)에서 **PASS 가 아님**(FAIL 또는 WARN), (b)에서 **FAIL**.
  - 정상·과다 라벨이 하나도 없는 조건(예: traffic_drop 위주)은 판정 불가로 기록(5.4).
- **절차**: 탐색 시드 7·11 로 C4' 동작을 확인(탐색, 판정 근거 아님) → 근거 시드 23·31·47 로 **1회** 판정. 근거 시드 결과로 기준·식·상수를 다시 고르지 않는다. C0·C3 열은 참고로 함께 출력.
- 추가 기록(판정 아님): traffic_drop 위주 조건의 G3 값.
- **집계 규칙 (근거 실행 전 고정, 2026-10-06 사용자 결정)**: 학습 모델 **`promo_s101` 과 `promo_s103` 둘 다** 근거 시드 23·31·47 로 실행한다. **두 모델 모두** 위 합격 기준을 충족해야 **V3 PASS**, 하나라도 FAIL 이면 **V3 FAIL**. 어느 모델이 더 낫다는 이유로 한쪽을 고르지 않는다. 판정 불가 조건 처리는 위 규칙 그대로(그 조건의 과다 기준만 판정 불가, 전 조건에 과다 라벨이 없으면 전체 판정 불가).
- **근거 실행 결과별 후속 (근거 실행 전 고정)**:
  - **V3 PASS** → G3(C4')를 승격 게이트의 **판정**으로 유지한다.
  - **V3 FAIL** → G3(C4')는 **정보·보조 신호**로 명시하고, 승격 판단은 **V1·V2·V4 오프라인 검증, G4 카나리, 사람 검토**에 둔다. 근거 결과를 보고 식·기준을 다시 고르는 재설계는 하지 않으며, G3 개선이 필요하면 **별도 과제로 plan.md Backlog 에 기록**한다.
  - **V3 판정 불가**(전 조건 과다 라벨 없음) → FAIL 과 같은 후속(정보·보조 신호).

## 7. 승격·롤백 절차 (운영)
1. **카나리 생성(선행 필수)**: `python validation/cli/build_canary.py --out-dir <모델 볼륨>` (두 트랙). 없으면 G4 SKIP.
2. **학습 요청**(트랙별): `/api/model/train` 에 `training_config={"epochs":30,"batch_size":64,"patience":5}`, `alert_policy="precision"`, `exclude_suspect=true`.
3. **게이트 확인**(UI 모델 관리): G1~G5 값·기준·`detail`. traffic 의 G2 FAIL 이 "활성 v1 비정상(val_loss 3.01)" 때문인지 메시지로 확인.
4. **승격**: `/api/model/promote`. G2 만 FAIL(활성 비정상)이고 G1·G4 PASS, G3 FAIL 아님(WARN 이면 `detail` 검토)이면 `force=true`, 승격 이력 사유에 "v1 비정상 기준(G2), P1-3 V1~V4 합격" 기록. 그 외 FAIL 이면 승격하지 않는다.
5. **확인**: Consumer 리로드, 정책 적용, `baseline_legacy=False`, 24h `warming_up`.
6. **롤백(필요 시)**: `/api/model/rollback` → v1. 정책도 기본으로 함께 복귀(B3).
7. `DRIFT_RETRAIN_MODE` 는 `candidate` 유지. auto 는 P1-1 설계서 8장 조건 충족 후 별도 결정.
8. 섀도 운영 중 정책 변경은 4.4 절차로만.
