## 1. 배경과 범위
- P1-3 V3 FAIL(2026-10-06) 후 G3 는 정보·보조 신호(P1-3 5.3), V5(2026-10-07)에서 G2 의 '너무 좋아진 쪽' 한계 확인(P1-3 2.4-1·10장). 그동안 승격 판단은 V1·V2·V4 오프라인 검증, G4 카나리, 사람 검토, 승격 사유 기록(P1-3 7장 3~4)에 둔다.
- 범위: (1) G3 의 상대 판정 대안 비교, (2) G2 검증 손실 판정의 방향 보완, (3) 채택 시 구현 단위. **범위 밖**: G1·G4·G5 변경, 알람 정책·임계치 산출(P1-5 종료), 카나리 구성, traffic_drop 판별(P1-4), 실데이터.

## 2. 선행 확인 — 현재 게이트 코드 사실 (2026-10-07, 코드로 확인)

### 2.1 공통 (`src/models/promotion_gate.py`, `src/models/registry.py`)
1. 게이트는 학습 직후 1회 실행해 레지스트리 엔트리 `gate` 에 저장, 승격은 저장값을 쓴다. `POST /api/model/gate` 로 재실행(`src/api/main.py` `run_gate_for`).
2. 종합: FAIL > WARN > PASS, **G3 SKIP 은 종합 WARN**, 다른 SKIP 무시(`overall_status`, 62-70). **auto 는 PASS 에서만 승격**.
3. 승격(`registry.promote` 253-267 → `_gate_findings` 221-243): G1 FAIL 은 force 로도 불가, **그 밖의 FAIL·ERROR 는 차단 사유(409, force 로 진행)**, WARN 은 승격하고 메모로 반환. 게이트의 비교 대상(`data.against`)이 현재 활성과 다르면 G2 차단 사유를 버리고 `compare_with_active` 로 다시 계산(lessons #34). 게이트가 없으면 `compare_with_active` 만 적용.

### 2.2 G2 (`check_g2` 92-101 → `registry.compare_with_active` 194-209)
1. 임계치: `tc/ta > 3` **또는** `< 1/3` 이면 경고(**양방향**). 상수 `THRESHOLD_RATIO_LIMIT = 3.0`(34).
2. 검증 손실: `vc/va > 3` 일 때만 경고(**나빠지는 쪽만**). 상수 `VAL_LOSS_RATIO_LIMIT = 3.0`(35). 어느 한쪽이 없거나 0 이면 비교 안 함. → **plan.md P1-6 ② 의 전제와 일치**.
3. **추가 사실(전제 보완)**: `final_val_loss` 는 각 모델의 **자기 검증 데이터**에서 구한 best 검증 손실(전 타임스텝 평균, `trainer.py:107-172`, `:321`)이다. 후보는 학습 당시의 홀드아웃 포트, 레거시 v1 은 다른 분할·데이터·스케일러 버그 수정 전(lessons #25) 산출물이다. 따라서 **검증 손실 비율은 같은 데이터에서 잰 비교가 아니며**, "후보가 비정상적으로 낮다" 와 "검증 데이터가 쉬웠다/달랐다" 를 구분하지 못한다. 활성 v1 의 3.01 이 왜 높은지는 **확인하지 않았다**(스케일러 버그 영향은 추정).
4. G2 FAIL 은 차단 사유(force 필요). G2 경고 문자열은 임계치·검증 손실 각각 한 줄.

### 2.3 G3 (`check_g3` 114-142, 데이터는 `run_gate` 245-305)
1. 데이터: `plan_window` 의 **최근 `gate_days`=3일**(`train_window.py:36`) 원본을 DB 에서 그대로 조회(`_fetch_raw_for_gate`, **정제 없음 → 실제 장애 구간 포함**), 홀드아웃 포트만(`_sample_ports`, salt `ptn`·10%, 최대 2000포트).
2. **후보·활성 모두 같은 원본·같은 구간**을 각자의 모델·각자의 알람 정책으로 점수화(274-289, P1-3 4.2-6) → `alerting.alarms_from_track_scores` → `count_incidents` 로 인시던트/포트·일.
3. 판정(C4'): 포트·일 < 150 이면 SKIP(→ 종합 WARN) → 상대 기준 `cand > max(active × 1.5, 0.01)` 이면 **FAIL** → 아니면 `cand > 0.05` 이면 **WARN** → PASS. 상수 `retrain_policy.py:62-65`.
4. **알람 단위 겹침** `overlap_with_active`(후보 알람 행 중 같은 포트·시각에 활성도 알람인 비율)를 계산해 `data.candidate_stats` 에 저장하지만 **판정에 쓰지 않는다**(290-293).
5. "G3 = 정보·보조 신호" 는 P1-3 5.3 의 **문서상 지위**다. 코드는 바뀌지 않아 **상대 FAIL 은 여전히 차단 사유(force 필요)**, WARN 은 auto 차단.
6. **비대칭(사실 + 미검증 영향)**: 게이트 포트는 후보에게는 학습에서 뺀 홀드아웃(조기 종료에만 사용)이지만, 활성 모델에게는 학습 포트였을 수 있다(다른 salt·레거시 v1 은 전 포트 학습). 활성의 알람이 그만큼 적게 나올 수 있으나 측정하지 않았다.

## 3. 사전 고정 원칙 (이 설계서의 전제)
1. **P1-3 결과를 다시 고르지 않는다**: V3 FAIL·G3 정보 신호 강등, V5 G2 PASS 는 기록 그대로. P1-6 의 어떤 결과도 P1-3 판정을 바꾸지 않는다(plan.md P1-6, lessons #37).
2. 대안은 2.4 의 이미 연 데이터를 보고 떠올렸다 → 그 데이터(시드 23·31·47)로 대안을 고르거나 판정하지 않는다. **선택은 개발 데이터, 판정은 미개봉 근거 데이터 1회**(#30).
3. 판정 기준은 **데이터를 열기 전에** 11장 결정으로 확정하고, 이후 변경은 6.4 규칙만.
4. 근거 실행은 **1회**, 코드 잠금으로 강제(P1-3·P1-5 `evidence_lock`·`check_record` 방식, #38).
5. 한 번에 하나: G3 대안은 **상대 FAIL 판정식만** 바꾸고 최소 포트·일 가드·절대 상한 WARN·종합 규칙은 그대로. G2 대안은 **검증 손실 판정만** 바꾸고 임계치 양방향은 그대로.

## 5. 대안 (게이트별, 한 번에 하나)

### 5.1 ① G3 — 상대 FAIL 판정식만 교체 (가드·절대 WARN·종합 규칙 고정)
