## 1. 배경과 범위

- **배경**: P1-2 는 원래 "실 이력 접근 불가를 가정하고 도구를 먼저 준비"하는 과제였다(plan.md). 2026-10-14 타겟 재정의로 "타겟 확정 후 시작"으로 미뤘고, 2026-10-15 사용자가 테스트망 실DB 의 테이블·컬럼·알람 체계를 직접 확인해 주어(2.1) 입력 스키마가 대부분 확정되었다. 정답(장애 티켓)은 여전히 없고, **EMS 알람 이력이 약한 정답**이다(`report_package.md` C3).
- **범위 안**: 읽기 전용 추출, 스냅샷 관리, 알람명 해석, 포트 조인 검증, 알람 에피소드 정의, AI·베이스라인 오프라인 재생, C1(원값)·C3·C4·C6·탐지 지연·유형별 집계, 현장 검토 샘플과 채점(C1·C2·C4a), 라이브 결과의 C5.
- **범위 밖**: 운영 모델 교체(활성화·승격), 알람 정책 변경·튜닝, 실데이터 재학습 중 9.7.5a 절차 밖의 것(하이퍼파라미터 탐색·추가 시드·다른 학습 구간), 운영 `src` 의 수정(2.2 의 fetch 필터 문제는 Q1 로 분리), RCA 룰 조정, 합격 기준 값 자체의 변경(P0-3 몫). 섀도 운영 절차 문서화는 `report_package.md` 5장을 따르고 이 설계는 도구만 다룬다.
- **원칙**: 이 도구는 `validation/` 에 둔다(`src` 는 import 하지 않음, `tests/test_architecture.py`). 정답(EMS 알람)은 평가에만 쓰고 학습 경로에 넣지 않는다(lessons #22).

EMS 스키마에 우연히 같은 이름의 테이블이 있으면 남의 데이터를 지울 수 있다 → `plan` 이 이름 충돌을 점검한다(4.9). 납품 현장(폐쇄망)의 DB 에도 같은 결정이 적용되는지는 별개다(이 결정은 **테스트망 한정**).

## 4. 데이터 접근 설계 (읽기 전용)

### 4.1 연결과 읽기 전용 보장

- 새 모듈 `validation/realdata/db_readonly.py`. `DBConnector` 를 생성하지 않는다(2.2-1). 접속 정보는 `src.config.DB_CONFIG` 를 import 해서 쓴다(운영과 같은 설정 방식 — 이 설계는 설정 파일 내용을 다루지 않는다). 단 **계정·비밀번호만** 도구 전용 환경변수 `RDC_DB_USER`·`RDC_DB_PASS` 가 있으면 그 값으로 바꾼다 → 운영 설정을 건드리지 않고 읽기 전용 계정(4.8)으로 실행할 수 있다.
- **권한 검사 (fail closed, 연결 직후·세션 설정 전, 모든 하위 명령 공통)**: `SHOW GRANTS FOR CURRENT_USER()` 의 각 줄을 파싱한다.
  - 허용: `GRANT USAGE ON *.* …`(권한 없음 표시), `GRANT SELECT ON <db>.* …`·`GRANT SELECT ON <db>.<table> …`(SELECT **단독**).
  - 거부: 그 밖의 모든 권한 단어(`ALL PRIVILEGES`, `INSERT`, `UPDATE`, `DELETE`, `CREATE`, `DROP`, `ALTER`, `INDEX`, `SUPER`, `FILE`, `PROCESS`, `RELOAD`, `PROXY`, `EXECUTE`, `CREATE TEMPORARY TABLES`, `LOCK TABLES`, `EVENT`, `TRIGGER` 등)과 `WITH GRANT OPTION` 이 **한 줄이라도** 있으면 실행을 거부하고 4.8 의 계정 생성 안내를 출력한다. 화이트리스트 방식이라 모르는 권한 단어도 거부된다.
  - `SHOW GRANTS` 자체가 실패하거나 파싱할 수 없는 줄이 있으면 거부(판단 불가 = 거부).
  - root(현재 사용자 계정, D12)는 `ALL PRIVILEGES … WITH GRANT OPTION` 이므로 **기본으로는 거부된다**. 이것이 기본 동작이다.
  - **예외 플래그 `--allow-write-account` (2026-10-16 확정, Q10·D15)**: 플래그가 있을 때만, 위 거부 사유(쓰기 권한 단어·`WITH GRANT OPTION`·파싱 불가 줄)가 있어도 진행한다. 규칙:
    1. **기본은 fail closed 그대로** — 플래그가 없으면 거부. 환경변수·설정 파일로 켜는 경로는 두지 않는다(명령줄에서 매번 명시).
    2. 플래그는 **권한 검사만** 건너뛴다. `SET SESSION TRANSACTION READ ONLY`·`MAX_EXECUTION_TIME`·문장 가드(SELECT/SHOW 만)는 그대로 적용된다 → 도구가 쓰기 문장을 보내지 않는다는 보장은 유지된다.
    3. `SHOW GRANTS` 실패(판단 불가)도 플래그로 진행할 수 있다. 단 **접속 실패·세션 설정 실패**(특히 `READ ONLY` 설정 실패)는 플래그와 무관하게 중단.
    4. 진행 시 표준 오류에 경고 1줄(거부 사유가 된 권한 단어 목록)을 출력하고, 매니페스트에 `privilege_check: "override"`, 거부 사유 권한 단어, 계정명(비밀번호 제외)을 기록. `report` 출력 머리에도 `privilege_check` 값을 표시한다.
    5. 모든 하위 명령(`plan`·`extract`·`live` 포함)에서 허용한다 — 판정(`judge`) 결과의 유효성은 계정 권한과 무관하므로(도구는 읽기만 함) 제한하지 않는다.
  - 근거와 한정: 사용자 결정(테스트망 DB 는 스키마가 분리돼 쓰기 무관, D15). **남는 위험**: 서버가 계정 권한으로 막는 마지막 방어선이 없고, 쓰기 계정 비밀번호를 분석 PC 환경변수(`RDC_DB_PASS`)에 둔다(유출 시 그 계정 권한 전체). 도구 밖의 실수(같은 셸의 다른 스크립트)는 막지 못한다. 그래서 **읽기 전용 계정(4.8)을 권장 경로로 유지**하고, 납품 현장 DB 에서는 이 플래그를 쓰지 않는 것을 기본으로 한다(현장 결정은 별개).
  - 결과(허용된 grant 줄 목록 또는 override 기록, 계정명 — 비밀번호 제외)를 매니페스트에 기록.
- 연결 직후 세션 설정: `SET SESSION TRANSACTION READ ONLY`, `SET SESSION MAX_EXECUTION_TIME = <ms>`(5.7.8+ 의 SELECT 시간 상한, 기본 60,000 [제안]), `SET SESSION time_zone` 은 **바꾸지 않는다**(DB 의 naive datetime 을 그대로 KST 로 해석, 4.6).
- **문장 가드**: 모든 쿼리는 `ro_query(sql, params)` 한 곳을 지난다. 주석 제거 후 첫 토큰이 `SELECT`·`SHOW` 가 아니거나 `;` 로 여러 문장이 이어지면 실행 전에 예외. 세션 설정 3개만 연결 함수 내부에서 예외로 허용.
- 3중 방어의 역할: **권한 검사**(계정 자체가 쓸 수 없음을 확인) → 세션 읽기 전용(서버가 쓰기 문장을 거부) → 문장 가드(도구 코드가 쓰기 문장을 만들지 않음). 앞의 둘이 서버 쪽 보장이고 문장 가드는 실수 방지용이다. `--allow-write-account` 사용 시에는 첫째가 빠지고 둘째·셋째만 남는다.
- 접속·조회 실패는 빈 결과로 넘기지 않고 예외로 중단(lessons #14).

### 4.2 테이블 탐색

- 종류별로 `information_schema.tables` 를 한 번씩 조회: `SELECT table_name, table_rows FROM information_schema.tables WHERE table_schema = DATABASE() AND table_name LIKE %s`(접두어 바인딩).
- 가져온 이름을 Python 정규식으로 분류·검증(**`LIKE 'cowptn_noti_pm_%'` 는 광 테이블도 잡으므로 정규식이 최종 판정**):
  - ETH: `^cowptn_noti_pm_(\d{4})_(\d{2})_(\d{2})_(\d{2})$`
  - 광: `^cowptn_noti_pm_optic_power_(\d{4})_(\d{2})_(\d{2})_(\d{2})$`
  - 알람: `^cowptn_noti_alarm_(\d{4})_(\d{2})_(\d{2})(?:_(\d{2}))?$` — 테스트망은 **일 단위**(K15 확정, D23). 정규식은 시간 단위 이름도 받는다(다른 환경 대비). 한 DB 에 두 형식이 섞여 있으면 `plan` 이 경고하고 둘 다 읽는다(같은 `id` 중복은 K4 중복 보고로 드러남)
- 정규식을 통과한 이름만 백틱으로 감싸 SQL 에 넣는다(값은 항상 `%s` 바인딩). 사용자 입력이 테이블명이 되는 경로는 없다.
- 요청 구간의 시간 목록과 대조해 **없는 시간 테이블 목록**(데이터 공백)을 출력한다(C5c 와 별개인 원본 공백).

### 4.3 기간·경계

- 구간은 반열림 `[start, end)`(KST naive). 성능 테이블은 `floor(start) − 1h ~ floor(end − 1s) + 1h` 의 시간 테이블을 읽는다. **`occur_date` 조건은 SQL 에 넣지 않는다**(2026-10-16 변경 — 쓰레기 값 행이 조용히 빠지면 격리 건수를 셀 수 없음, D18). 4.3a 격리 후 정상 행만 `occur_date >= start AND occur_date < end` 로 Python 에서 거른다.
- 알람은 `floor(start) − lookback ~ floor(end − 1s) + 1h` 의 테이블을 읽고, 4.3a 격리 후 `occur_date < end AND (release_date IS NULL OR release_date >= start)` 로 Python 에서 거른다(K5).

### 4.3a 시각 신뢰 기준과 격리 (2026-10-16 추가 — D18, D11 보완) [제안: ±1.5시간]

- **신뢰 기준 = 테이블 시각**: 행이 들어 있는 테이블 이름의 시각 `H`(시간 테이블은 `YYYY-MM-DD HH:00`, 일 테이블은 그 날짜 00:00 ~ 다음 날 00:00 구간 — 테스트망 알람은 일 테이블, K15·D23).
- **정상 행**: `H − 1.5h ≤ occur_date ≤ H + 1h + 1.5h`(시간 테이블; 테이블이 덮는 1시간 `[H, H+1h]` 앞뒤로 1.5시간 여유. 일 테이블은 `[날짜 − 1.5h, 다음 날 + 1.5h]`). 정상 행에만 D11(구간 끝) 해석을 적용하고 `round('15min')`(5.2) 한다.
- **격리 행**: 그 밖(2012·2025·2027 등), `occur_date` NULL, 알람의 `release_date < occur_date`. 격리 행은 **분석에서 제외**하고 시각을 테이블 시각으로 추정해 살리지 않는다(한 시간 테이블 안의 4개 15분 구간 중 어디인지 알 수 없음 — 추정하면 값이 다른 구간에 들어가 단절·급감 신호를 만들 수 있음). 원본은 스냅샷의 `quarantine/` 에 그대로 보관.
- 보고(`extract` 매니페스트·`plan` 표본): 종류별 격리 행 수·비율, 장비(`ip_addr`)·`system_type` 별 격리 비율, `occur_date` 의 연도 분포, 격리 표본 20행, **정상 행의 `occur_date − H` 분포**(15분 단위, K3).
- 격리가 특정 장비에 몰리면(장비 격리 비율 > 50%) 그 장비를 `quarantine_heavy` 로 표시하고 판정 출력 아래에 목록으로 낸다(판정에서 빼지는 않음 — 정상 행만 쓰므로 자동으로 성능 공백이 됨, 9.4).
- 근거·한정: ±1.5시간은 lead 제안값이다. 경계 행(정각)이 앞·뒤 어느 테이블에 들어가는지(K3) 정도의 어긋남은 허용하고 연 단위 쓰레기 값만 거르는 폭이다. 격리 후 같은 `(포트, 15분 구간)` 이 두 테이블에서 나오면 K7 중복 규칙(마지막 행 유지)으로 처리하고 건수를 보고한다. 쓰레기 값의 원인(장비 시계 오류 등)은 모른다 [추정 불가].
- `plan` 은 경계 시간 테이블 2개에서 `MIN/MAX(occur_date)` 를 읽어 테이블 시간과 `occur_date` 의 관계를 출력한다(K3 확인용).

### 4.4 필터와 스키마 프로필

| 종류 | 필터 (기본, `--schema real`) | `--schema sim` (`cowptn_test`) |
|---|---|---|
| ETH | `signal_type = 6 AND time_type = 1` | `signal_type = 6` (time_type 컬럼 없음) |
| 광 | `signal_type = 44 AND time_type = 1` (K6) | 필터 없음 (컬럼 없음, 2.2-6) |
| 알람 | 없음 (`signal_type` 은 알람에서 안 씀, D5) | 알람 테이블 없음 → 알람 기능 SKIP |

- 프로필은 테이블별로 `information_schema.columns` 를 조회해 **필터 컬럼이 있는지** 확인한다. `real` 에서 필터 컬럼이 없으면 그 테이블을 오류로 중단(조용히 필터를 빼지 않음). `sim` 은 없을 때만 생략하고 생략 사실을 매니페스트에 남긴다.
- `plan` 은 표본 테이블(구간 첫·마지막 시간)에서 `signal_type`·`time_type` 별 행 수를 `GROUP BY` 로 보고한다 → 2.2-2 의 오염 여부를 수치로 확인.
- 포트 필터: `--ports <CSV>`(열 `ip_addr`, 선택 `cid`, `lid`). `ip_addr` 은 SQL `IN (%s, …)` 바인딩(1회 1,000개 이하로 분할), `cid/lid` 는 Python 에서 거른다(세 테이블 같은 규칙). 알람의 장비 단위 행(`cid=0` 또는 `lid=0`, 6.1)은 포트 필터와 무관하게 **필터한 장비(ip_addr)의 것은 모두** 남긴다(HW 동시 발생·작업 대용 표시에 필요).

### 4.5 청크·행 수 상한

- 테이블마다 키셋 페이지: `SELECT … FROM \`t\` WHERE <필터> AND id > %s ORDER BY id LIMIT %s`(기본 청크 50,000 [제안]). `OFFSET` 은 쓰지 않는다. `id` 가 없거나 PK 가 아니면(확인: `information_schema.columns` / `statistics`) 그 테이블은 `LIMIT` 없이 1회 조회하되 테이블별 행 상한을 적용.
- **전체 행 상한** `--max-rows`(기본 **2,000,000** [제안, 2026-10-16 재계산 — lead 실측 D17·D20 기준, 아래 표]): `plan` 단계에서 `table_rows`(InnoDB 추정치)의 합이 상한을 넘으면 `extract` 를 시작하지 않고 구간·포트를 줄이라고 안내. 추출 중 실제 누적(증분 추출은 스냅샷 누적)이 상한을 넘어도 즉시 중단하고 부분 스냅샷을 "불완전"으로 표시. `plan` 은 종류별(ETH·광·알람) 추정 행 수와 표본 시간 테이블의 고유 포트 수를 함께 출력한다.
- **예상 규모 (2026-10-16, lead 실측 기준)** — 개정 2 초안의 "2,000포트 × 96 × 92일 ≈ 17.7M" 가정은 실측과 크게 달라 폐기했다(실제 238포트, 데이터일 57일, 포트·일당 행 수도 96 보다 적음):

  | 종류 | 근거 | 현재(07-10~10-12) | (참고) 16주 더 쌓일 경우 |
  |---|---|---|---|
  | ETH (`signal_type=6`, `time_type=1`) | D17 실측 31.7만 행(격리 대상 3.4만 포함) ≈ 주당 2.35만 | **약 0.32M** | + 약 0.38M [추정: 같은 수집 패턴 유지] |
  | 광 (`signal_type=44`) | D19: 전 테이블 0행 | **0** | 0 (수집이 생기면 `plan` 에 드러남) |
  | 알람 | D20 실측 46,594건, 9월 기준 월 1.6만 ≈ 주당 3.7천 | **약 0.05M** | + 약 0.06M |
  | 합계 | | **약 0.37M** — 대안 1 의 추출 전체 | 약 0.8M → 상한 **2M**(Q13 확정, 현재의 약 5배·16주 누적의 약 2.5배) |

  - 상한 검사는 필터 전 `table_rows`(InnoDB 추정치, 오차 큼) 기준이라 ETH 테이블에 다른 `signal_type` 행이 많으면(2.2-2) 실제 추출 행보다 크게 잡힌다. 넘으면 `plan` 의 종류별 표를 보고 `--max-rows` 를 추정치 × 1.2 로 올려 다시 실행한다(상한은 실수로 너무 넓은 구간·다른 DB 를 읽는 것을 막는 장치이지 판정 기준이 아님). 개정 1 의 기본 1천만은 이 규모에서 장치로서 의미가 없어 낮췄다.
  - 쿼리 수: ETH 시간 테이블 약 2,280개(95일 × 24) + 광 2,248개(모두 0행이지만 조회는 함 — `table_rows` 추정치가 0 이어도 실제 0 인지 확인) + 알람 94개(일 테이블) 또는 약 2,260개(시간 테이블, K15) ≈ 4,600~6,800 SELECT. ETH 테이블당 평균 약 140행이라 청크(50,000) 1회로 끝난다. 소요 시간은 실DB 에서 측정.
  - 디스크(스냅샷 `csv.gz`): 수십 MB 이하 [추정]. 메모리: 전체를 한 번에 올려도 문제없는 규모라 `replay` 의 포트 묶음 분할은 두지 않는다(개정 2 초안의 200포트 묶음 철회).
- 추출은 일 단위 파일로 흘려 쓴다(메모리에 전체를 올리지 않음). `stop_checker` 패턴(lessons #7)으로 중단 가능.

### 4.6 시간대

- DB 의 `occur_date`·`release_date` 는 **KST naive** 로 가정하고 변환하지 않는다 [확인 D1]. 스냅샷·출력의 모든 시각 열은 KST naive 이며 매니페스트에 `"tz": "Asia/Seoul (naive)"` 를 기록.
- `plan` 은 최신 테이블의 `MAX(occur_date)` 와 실행 호스트의 현재 시각 차이를 출력하고, 차이가 8~10시간이면 "시간대 의심" 경고(lessons #27 — 컨테이너 UTC 문제 재발 방지). 판정은 하지 않음.

### 4.7 스냅샷 (DB 는 한 번만 읽는다)

- 위치: `validation/runs/p1_2/<run_id>/raw/` (git 제외, 2.2-8). 형식: 종류·일자별 `csv.gz`(새 의존성 없음 — parquet 은 의존성 확인 후 선택 사항).
- `manifest.json`: 실행 시각, 도구 버전(git 커밋), DB 이름(호스트·계정은 기록하지 않음), 구간, 포트 필터, 스키마 프로필, 읽은 테이블 목록과 테이블별 행 수, 없는 시간 테이블, 필터 밖 행 수(2.2-2), 중복 키 수(K7), 값 범위(K8), lookback 경계 알람 수(K5), 완료/불완전 여부.
- 이후 하위 명령은 모두 `--run <run_id>` 의 스냅샷만 읽는다. 분석을 바꿔 다시 돌려도 DB 를 다시 읽지 않는다.
- **증분 추출(`--append-to`)은 구현하지 않는다**(Q12 로 대안 1 확정 — 판정은 첫 전체 추출 `[S, D)` 만 사용). 설계는 부록 B 에 보관하며, `D` 이후 새 데이터로 새 판정 기간을 두기로 하면 그때 함께 구현한다. 따라서 "진행 중 알람이 있는 알람 일 파일을 불완전으로 표시해 다음 증분 때 병합" 같은 갱신 경로도 **두지 않는다**(2026-10-16, dev U2 질의에 대한 답). 스냅샷은 추출 시점의 상태로 고정되며, 진행 중 알람은 아래 시점 고정 규칙과 F3 로 처리한다.
- **일 파일 경계 (2026-10-16 명시, dev U2 질의 확인)**: 성능 행은 4.3a 정상 행의 `round('15min')` 한 `occur_date`(구간 끝, D11)의 **날짜**, 알람 행은 `occur_date` 의 **날짜** 파일에 넣는다. 성능 `occur_date = 00:00` 행은 앞날 23:45~00:00 구간 값이지만 날짜 기준상 다음 날 파일에 들어간다. 데이터일(9.7.1)·기간 필터(4.3 `occur_date >= start`)·`J0` 경계도 같은 `occur_date` 기준이라 서로 일관되며, 이 15분 어긋남은 그대로 둔다(판정 구간 첫 행이 개발 기간 마지막 15분 구간 값일 수 있음 — 영향은 포트당 1슬롯).
- **알람 시점 고정 규칙 (2026-10-16 추가 — 결과가 추출 날짜에 좌우되지 않게)**: 추출은 `D` 이후에 실행되므로(예: 10-17 실행), `D` 전에 시작해 `D` 이후에 해제된 알람은 추출 때 `release_date ≥ D` 로 보인다. 같은 알람이 추출 날짜에 따라 "진행 중" 또는 "해제됨"으로 달라지지 않도록, **분석 단계에서 `release_date IS NULL` 또는 `release_date > D` 인 알람은 모두 `ongoing = True`, 끝 = `D` 로 자른다**(F3 의 "스냅샷 `end`" = `D`). 원본 `release_date` 는 스냅샷에 그대로 보관하고 매니페스트에 `D` 이후 해제된 알람 수를 기록한다. 판정 기간 끝이 `D` 이므로 그 뒤의 해제 시각은 판정에 쓰이지 않는다.

### 4.8 운영 절차 — 읽기 전용 계정 만들기 (도구 실행 전 1회, 사용자/DBA)

> 도구는 플래그 없이는 root 로 실행되지 않는다(4.1). **권장 경로**는 아래 읽기 전용 계정이고, 테스트망에서는 `--allow-write-account` 로 기존 계정을 쓸 수도 있다(Q10). 아래 절차를 **도구 문서**(dev 가 `validation/README.md` 의 `real_data_check` 절과 `real_data_check.py --help` 의 거부 메시지에 같은 내용)로도 제공한다.

1. 관리자 계정(root)으로 EMS DB 서버에 접속해 계정을 만든다. **호스트는 도구를 실행하는 PC 의 IP(또는 좁은 대역)로 제한**하고 `'%'` 는 쓰지 않는다.
   ```sql
   -- MySQL 5.7. <EMS_DB> = 성능·알람 테이블이 있는 스키마 이름, <분석PC_IP> = 도구 실행 PC
   CREATE USER 'ptn_ro'@'<분석PC_IP>' IDENTIFIED BY '<충분히 긴 비밀번호>';
   GRANT SELECT ON `<EMS_DB>`.* TO 'ptn_ro'@'<분석PC_IP>';
   SHOW GRANTS FOR 'ptn_ro'@'<분석PC_IP>';
   -- 기대 출력 2줄: GRANT USAGE ON *.* TO ...  /  GRANT SELECT ON `<EMS_DB>`.* TO ...
   ```
   - 같은 대역의 여러 PC 가 필요하면 `'ptn_ro'@'10.1.2.%'` 처럼 좁은 대역만.
   - `information_schema` 는 따로 권한을 줄 필요가 없다(SELECT 권한이 있는 스키마의 테이블만 보인다 — MySQL 5.7 동작, 실DB 에서 `plan` 으로 확인).
   - 결과 테이블(`anomaly_detection`)을 라이브 C5 용으로 읽어야 하고 그것이 다른 스키마에 있으면 그 스키마에도 `GRANT SELECT` 만 추가한다.
2. 도구 실행 PC 에서 계정을 환경변수로 준다(비밀번호를 파일·저장소·명령 이력에 남기지 않는다): `RDC_DB_USER=ptn_ro`, `RDC_DB_PASS=…` (4.1). 호스트·포트·DB 이름은 기존 설정 방식 그대로.
3. `real_data_check.py plan …` 를 실행해 권한 검사 통과(매니페스트의 grant 줄)를 확인한다.
4. 계정을 지울 때: `DROP USER 'ptn_ro'@'<분석PC_IP>';`
5. 읽기 전용 계정을 만들지 않고 쓰기 계정(root 등)으로 실행하려면 `--allow-write-account` 를 명시한다(4.1 규칙 1~5, 테스트망 한정 권고). 거부 메시지에 이 두 경로를 함께 안내한다.

### 4.9 결과 테이블 이름 충돌 점검 (`plan`, 2026-10-16 추가 — Q11 의 후속)

- 사용자 결정(Q11)으로 운영 결과(`anomaly_detection`)가 EMS 와 같은 DB 에 생길 수 있으므로, `plan` 은 `information_schema.tables` 에서 현재 스키마의 `anomaly_detection` 존재 여부와, 있으면 `information_schema.columns` 의 컬럼 목록을 출력한다(읽기만).
- 판정: 컬럼 집합이 운영 테이블 정의(`db_connector.py:47` 의 컬럼, dev 가 상수로 고정)의 상위집합이면 "운영 결과 테이블로 보임", 아니면 **"이름 충돌 의심 — 운영 서비스를 이 DB 로 기동하지 말 것"** 경고(서비스 기동 시 `CREATE TABLE IF NOT EXISTS` 가 기존 테이블을 그대로 쓰고 `delete_old_data` 가 행을 지움, 2.2-9). 도구 동작은 바꾸지 않는다(경고만).

  - **원칙**: 행 분류는 **원 `cid`** 로 하고, 보정 키(`cid_j`)는 포트·slot 행에만 만든다(6.3). address 는 행을 **판정에서 빼는 방향으로만** 쓰고(규칙 1·7·7b·8), 키가 포트 모양이 아닌 행을 address 로 포트에 끌어들이지는 않는다. 규칙 7a 는 예외처럼 보이지만 키가 이미 포트 모양(`cid > 0, lid > 0`)인 행을 개정 4 의 제외에서 되돌리는 것이고, 키(`cid − 1`, `lid`)로 성능과 맞는다는 관찰에 근거한다. 빈 address 는 아무것도 보여 주지 않으므로 키 판단을 따른다(규칙 10). 이렇게 하면 분류가 틀렸을 때의 피해는 "실제 포트 알람 일부가 판정에서 빠짐"(과소 계수)으로 한정되고 아래 출력으로 크기가 보인다.
  - **dev 구현과의 차이**: 현재 `classify_alarm_rows`(`validation/realdata/port_join.py:51`)는 규칙 8 의 행을 `port` 로 분류한다 → `unit` 으로 바꾸고 규칙 ID 열(`row_rule`)을 남긴다. 규칙 1~4·6·7 은 dev 구현을 승인한다. 개정 6 에서 `MAIN-Pn` 은 확인을 거쳐 규칙 7a 로 포트가 되었다.
  - **고정 출력 (dev 에 요청됨 — 승인)**: `join-check` 와 `alarms --summary` 는 **system_type(모델) × 규칙 ID** 건수 표와 개정 1 규칙(`cid=0`/`lid=0`)으로 분류했을 때와 달라진 행 수(재분류 건수)를 **항상 같은 순서로** 출력하고 매니페스트에 기록한다. 추가로 `slot_addr`·`unit_addr` 행 중 **같은 키의 성능 포트가 있는 행 수**와 표본 20행을 모델별로 낸다 — 이 수가 크면 그 표기가 실제 포트일 가능성이 있으므로 사용자 확인 후 **잠금 전에만** 규칙을 고칠 수 있다(변경 이력에 남김, 9.7.6).
  - **기간 한정**: 잠금 전 이 출력은 **개발 기간 `[S, J0)` 의 알람만** 대상으로 한다(P4). 위 2026-10-16 건수가 스냅샷 전체 기준이면 원 알람 수준의 판정 구간 노출로 9.7.2 에 함께 기록한다(범위는 dev 확인 필요).
  - 분류 규칙(규칙 ID 와 순서, 표 버전 **`row_class_v3`**(개정 6: 7a·7b 추가), `MAIN-Pn` 정규식 포함)은 설정 해시(9.7.3-4)에 포함한다. 재분류 건수 고정 출력은 개정 1 규칙 대비와 함께 **`row_class_v2` 대비**(`unit_addr` → `port_main` 건수, 모델별)도 낸다.
- **address 진단 열(조인 키 아님, 개정 5 에서도 진단용만)**: `addr_port = norm_port(address)` — 정규식 `S\.\s*(\d+)\s*-\s*P\s*(\d+)` 의 **마지막** 일치를 `S.<n>-P<m>` 으로(성능 `'CA216-UT7320-S.1 -P1'` → `S.1-P1`, 알람 `'S.2 -P1  '` → `S.2-P1`), 일치가 없으면 `S.<n>`, 그것도 없으면 `MAIN-P\s*(\d+)` 의 마지막 일치를 `MAIN-P<n>` 으로(개정 6 — 성능 address 안의 `MAIN` 포트와 알람 `MAIN-Pn` 을 J1·J2 에서 대조하기 위함), 모두 없으면 빈 값. 규칙 8 의 "`addr_port` 가 빈 값" 판단은 이 확장 전 기준(`S.n`·`S.n-Pm` 아님)으로 한다. 세 테이블 모두 스냅샷에 보관하고 **대조(J2·J0s)와 6.1 행 제외 판단에만** 쓴다.
- 알람 `p5_cid`·`p5_lid` 는 조인에 쓰지 않고 `p5_same = (p5_cid = cid AND p5_lid = lid)` 열만 남긴다(K1b).

### 6.2 키 결정의 경과 (D13 → 개정 5)

- 초안은 "성능 cid=1 ↔ S.1, 알람 cid=3 ↔ S.2" 관찰을 근거로 address 조인을 택했다. 그 두 샘플은 **서로 다른 장비 모델(system_type 12 = CE73K0 와 31 = CE7080)** 의 것이라 같은 포트가 어긋난다는 근거가 되지 못해, 개정 1 에서 사용자 판단에 따라 `(ip_addr, cid, lid)` 그대로 맞추는 조인으로 바꿨다(D13).
- **개정 5 (2026-10-16 사용자 결정 Q16 — D13 개정)**: 개발 구간 실데이터에서 그대로 맞추는 조인은 맞지 않았다. [확인 — dev 실행 출력, 개발 구간만, 파일은 git 제외]
  - 성능 `cid` 는 address 슬롯과 같거나(모델 12·13·22·31·33) 슬롯 + 1(9·11·28)이다.
  - 알람 `cid` 는 슬롯 + 1(7·10·12·13·22·31·33) 또는 슬롯 + 2(9·11·28)다. 성능이 있는 모델에서는 모두 **알람 `cid` = 성능 `cid` + 1** 로 일관된다.
  - `lid` 는 양쪽 모두 address 포트 번호와 100% 같다.
  - 키 매칭률(J4): 그대로 18.2% → 알람 `cid − 1` 85.4%(`− 2` 는 70.7%). 오프셋 스캔(알람 `cid` + 오프셋): −1 → 0.917, 0 → 0.170, +1 → 0.028. 그대로 맞춘 조인의 J2 address 불일치율 1.0, 슬롯 차이 최빈값 −1.
  - J3 는 장비 수집 공백 때문에 판별력이 부족했다. 장비 생존 구간으로 한정하면 `− 1` 보정 조인 일치율 a = 0.181, 대조군 0.049.
- 사용자는 **알람 `cid` 오프셋 보정**을 채택했다. 잘못된 키로 판정하는 것을 막는 안전 검사(6.3)는 보정 키 기준으로 다시 쓴다. 현장(EMS 화면) 대조는 하지 못한다(M1 미실시, 6.3 끝).

### 6.3 안전 검사 J1~J4 와 판정 규칙 (개정 5 — 보정 키 기준으로 다시 씀)

| 단계 | 내용 | 출력 |
|---|---|---|
| **J0s** 오프셋 스캔 (개발 구간만) | 모델별로 `k ∈ {0, 1, 2, 3}` 각각의 J4 매칭률과 J2 address 일치율 | 모델 × `k` 표, 최선 `k`·차선과의 차이, 모델별 포트 알람 수 |
| **J1** 성능 키 일관성 | 성능(ETH) 안에서 장비별로 `(cid, lid) ↔ addr_port` 가 1:1 인지. ETH 와 광 키의 겹침(광이 있을 때만) | 1:1 포트 비율, 1:1 아닌 포트 목록 |
| **J2** address 대조 | 보정 키로 조인된 알람·성능 쌍 중 양쪽 `addr_port` 가 모두 `S.n-Pm` 인 쌍에서 address 가 같은 비율(**system_type 별**), 슬롯 차이 분포, `p5_same` 비율(K1b). device·slot·unit 알람의 address 형태 | 모델별 일치율, 불일치 표본 20행 |

(a) 보정 키 조인, (c) 대조군 = 같은 장비의 다른 임의 포트(고정 난수 시드 0), 진단용 (b) 그대로 맞춘 조인·(d) `addr_port` 조인 | 조인별 일치율(에피소드 평균), 생존 구간 슬롯 수, 대상 에피소드 수 |
| **J4** 커버리지 | 포트 알람 중 보정 키의 성능 포트가 있는 비율. **분모는 성능 스냅샷에 있는 장비(`ip_addr`)의 포트 알람만**(성능이 아예 없는 알람 장비 — D22 의 70 대 60 — 는 따로 셈) | 모델별 매칭률, 못 찾은 알람 표본 20건 |

**보정 키와 오프셋 표 (사전 고정 절차)**:
- 조인 키 = `(ip_addr, cid_j, lid)`, `cid_j = 알람 cid − k(system_type)`(성능 쪽은 그대로). `k` 기본값 = 1.
- **모델별 예외는 개발 구간 J0s 로만 정한다**. 모델 `m` 의 포트 알람(개발 구간, 성능 장비 한정)이 **30건 이상**이고, 최선 `k*` 의 J4 매칭률이 **0.8 이상**이며, `k = 1` 보다 **0.2 이상** 높을 때만 `k(m) = k*` 로 둔다. 그 밖에는 1 이다. 현재 dev 집계로는 성능이 있는 모든 모델이 1 이라 예외가 없을 것으로 보인다 [추정 — 모델별 표는 dev 출력으로 확정].
- 결과는 설정 파일 `validation/realdata/alarm_cid_offset.csv`(`system_type, k, n_alarms, j4_at_k, j4_at_1, basis`)에 적고 **설정 해시(9.7.3-4)에 포함**한다. 확정은 **잠금 전**이며 잠금 뒤에는 바꾸지 않는다(바꾸면 판정 거부, 9.7.6). 표에 있는 모델도 `k` 를 판정 결과를 보고 바꾸지 않는다.
- **표에 없는 system_type**(개발 구간에 포트 알람이 30건 미만이거나 성능이 없던 모델): 기본 1 을 적용하고, 판정 실행 안에서 그 모델의 J4·J2 를 계산해 **J4 < 0.8 또는 J2 < 0.9** 이면 그 모델의 이벤트를 판정에서 빼고 `offset_unverified` 로 건수·장비를 보고한다. 이 검사는 판정 모델 결과를 보지 않는 키 검사라 판정 실행 안에서 해도 된다(규칙은 지금 고정).
- `cid_j ≤ 0` 이 되는 포트 알람은 `bad_key` 로 보고 판정에서 뺀다. 6.1 분류는 **원 `cid`** 로 먼저 한 뒤(256·0 등 장비 표기는 원 값 기준) 포트·slot 행에만 `cid_j` 를 만든다. slot 알람의 작업 대용 범위(8.6)도 `cid_j` 로 같은 슬롯의 성능 포트를 찾는다.
- 이후 모든 계산(F1~F8 에피소드 키, C3, 탐지 지연, 태깅)은 `cid_j` 를 쓰고 원 `cid` 는 스냅샷·출력에 함께 남긴다. dev 의 진단용 `--diag-key-shift` 는 개발 실행 전용으로 남기고(판정 실행 금지, 현행 그대로), 공식 키는 오프셋 표만 쓴다.

**판정 (사전 고정 — 개정 5)**: 개발 구간 결과로 `join_status` 를 정하고 잠금 파일에 기록한다.
- `verified` = 다음을 **모두** 만족: (i) J1 1:1 ≥ 95%, (ii) 오프셋 표의 모든 모델에서 J4 ≥ 0.8, (iii) 같은 모델들에서 J2 ≥ 0.9, (iv) J3 대상 에피소드 ≥ 5 이면 a > c(방향만 확인). J3 대상 < 5 이면 (iv) 는 `j3_insufficient` 로 표시하고 막지 않는다.
- 하나라도 미충족 → `failed`: C3·탐지 지연은 산출하되 판정에 쓰지 않고 **멈춰서 보고**한다. address 조인(d)이나 다른 `k` 가 기준을 만족해도 **자동으로 바꾸지 않는다**(사용자 결정 사항).
- **J3 의 한계와 기준 변경 (명시)**: 개정 1~4 의 J3 기준(일치율 ≥ 0.8, a − c ≥ 0.5)은 버린다. 테스트망은 장비 단위 수집 공백이 많아(D17·K17 장비 꺼짐) 공백 구간에서는 대상 포트와 대조군이 **함께 비어** "행 없음"이 일치로 세지므로 두 조인을 가르지 못한다. 생존 구간으로 한정해도 단절 알람 구간의 rx=0 비율이 낮아(a = 0.181) 크기 기준을 둘 근거가 없다(단절 알람의 발생 조건을 모름, 질문지 Q1-3). 그래서 J3 는 **방향 확인(a > c)만 하는 보조 검사**가 되었다. 이 변경은 개발 구간 결과를 본 뒤 정한 것이며, 판정 구간을 열기 전이다(lessons #37). 키를 받치는 근거는 J4·J2(데이터 일관성)다.
- **판정 구간에서의 해석 (사전 고정)**: 판정 실행은 판정 구간 데이터로 J1·J2·J4·J3 를 다시 계산해 보고한다. (1) 판정 구간 전체 J4 < 0.8 또는 J2 < 0.9 → `join_status_judge = degraded`, C3·탐지 지연 **판정 보류**(9.7.4). (2) 표에 없는 모델은 위 `offset_unverified` 규칙. (3) J3 는 판정에 쓰지 않는다: 대상 ≥ 5 이고 a ≤ c 이면 경고 문구만 붙이고, 대상 < 5 이면 "J3 판별 불가"를 적는다. 수집 공백이 많은 기간이면 J3 이 판별력이 없다는 점을 같은 표에 적는다.
- J4 의 0.8, J2 의 0.9 는 dev 개발 구간 값(매칭률 85.4%, 오프셋 스캔 0.917)을 본 뒤 정한 값이다. 오프셋 스캔 0.917 이 어떤 지표(매칭률 또는 address 일치율)인지와 보정 키 기준 J2 일치율 자체는 dev 출력으로 확인한다 [확인 필요 — J2 가 0.9 에 못 미치면 `failed` 로 멈추고 보고하며 기준을 낮추지 않는다]. 우연 매칭을 배제하는 최소선으로 정했고 판정 구간 결과를 보고 바꾸지 않는다.

**address 조인은 진단용으로만 남긴다 (개정 5 명시)**: `addr_port` 는 조인 키가 아니다. J2 의 대조와 J3 (d) 참고치, 6.1 의 행 제외 판단에만 쓰고, 어떤 경우에도 판정 조인을 address 로 바꾸지 않는다. 그대로 맞춘 조인(`k = 0`)도 J3 (b)·J0s 의 진단 열로만 남긴다.

**M1 수동 확인 — 미실시 (개정 5)**: 사용자가 EMS 화면 대조를 할 수 없다고 했다. 그래서 키 보정의 근거는 데이터 일관성(J4·J2·J0s)뿐이다. 모든 판정 보고와 `join-check` 출력에 다음 문구를 **고정**한다: **"키 보정은 데이터 일관성으로만 확인, 현장 대조 미실시"**. 나중에 `join_manual.csv`(`ip_addr, system_type, perf_cid, perf_lid, alarm_cid, alarm_lid, note`)가 들어오면 보정 키와 비교하고, 한 건이라도 다르면 J 판정과 무관하게 멈춘다(잠금 뒤에 들어오면 판정 결과에 그 사실을 덧붙여 보고).

## 7. 알람명 해석

### 7.1 1회성 변환기 `validation/cli/convert_alarm_tables.py`

- 입력: 사용자가 가진 C 소스 텍스트 파일(1개 이상). 출력: 알람명 JSON 1개.
- 파싱 대상:
  1. `enum_sys_id` enum → `{값: 모델명}`. 값이 생략된 항목은 C 규칙대로 직전 값 + 1. 주석(`//`, `/* */`) 제거.
  2. 배열 `lpsztbl_<MODEL>_ALM_RSN[]` → 문자열 목록(인덱스 = 배열 위치). 이름이 정확히 `^lpsztbl_([A-Za-z0-9]+)_ALM_RSN$` 인 배열만 채택하고, 그 밖의 `lpsztbl_*`(예: `lpsztbl_CE7080_ALM_RSN_4STEP`)은 **무시 목록**으로 출력(D6).
  3. 원소가 문자열 리터럴이 아니면(`NULL`, 매크로, 지정 초기화자 `[n] = …`) **변환 실패로 중단**하고 위치를 출력(조용히 건너뛰면 인덱스가 밀림). 인접 문자열 연결(`"A" "B"`)은 C 규칙대로 합침. 빈 문자열 `""` 은 허용하고 "빈 이름"으로 표시.
- 대조 검사: 파싱한 enum 이 2.1 D7 의 목록과 다르면 경고(값·이름 차이 표). D8 의 "표 있는 모델" 중 배열이 없는 모델, 배열은 있는데 enum 에 없는 이름을 출력.
- 출력 JSON 구조:
  ```json
  {"source_sha256": ["..."], "generated_at": "...", "code_offset": 367,
   "sys_id": {"31": "CE7080", "10": "CE7300S", "...": "..."},
   "tables": {"CE7080": ["...", "..."], "CE7300": ["..."]},
   "table_alias": {"CE7300S": "CE7300"},
   "ignored_arrays": ["lpsztbl_CE7080_ALM_RSN_4STEP"],
   "models_without_table": ["CE8310", "CE5300", "CE5500", "CE1830"]}
  ```
  `table_alias` 는 변환기 인자 `--alias CE7300S=CE7300`(D8 확인분)로만 넣는다(이름 유사성으로 추측하지 않음). 7700Q/Q2/Q2V 의 공유 여부는 K11 — C 소스에 배열이 각각 있으면 각각 쓰고, 없으면 사용자 확인 후 별칭 인자로.
- **저장 위치 (Q2, 2026-10-15 확정)**: **git 제외** — `validation/runs/ref/alarm_names.json`(이미 `.gitignore:45` 의 `validation/runs/` 아래라 설정 변경 불필요). 이유: 원문이 장비 소스 코드 일부이고 저장소 공유 범위에 넣어도 되는지 확인되지 않음, C 소스만 있으면 재생성 가능(`source_sha256` 로 동일성 확인). 저장소에는 변환기와 **합성 C 소스 픽스처**(테스트용 가짜 모델 2개)만 둔다. 저장소에 넣어도 된다고 사용자가 정하면 `validation/realdata/ref/alarm_names.json` 으로 옮기고 sha 를 테스트로 고정.

### 7.2 이름 조회 규칙

```
model  = sys_id.get(str(system_type))            # 없으면 → UNKNOWN-SYS-<system_type>
table  = tables.get(table_alias.get(model, model))
code   = alarm_type − 367
name   = table[code]   if table and 0 <= code < len(table) and table[code] != ""
```

| 경우 | `alarm_name` | `name_status` | 타겟 유형 |
|---|---|---|---|
| 정상 조회 | 표의 문자열(앞뒤 공백 제거) | `ok` | 7.4 매핑 |
| code 가 범위 밖·음수 | 표시명 형식 설정값(기본 `ALM-ID-{code}`, K10) | `out_of_range` | **미분류** |
| 표의 값이 빈 문자열 | `ALM-EMPTY-{code}` | `empty` | **미분류** |
| system_type 이 enum 에 없음 | `UNKNOWN-SYS-{system_type}-{alarm_type}` | `unknown_model` | **미분류** |
| 모델은 있으나 **표 없음**(CE8310·CE5300·CE5500·CE1830 등) | `NOTABLE-{model}-{alarm_type}` | `no_table` | **미분류** |

### 7.3 표 없는 모델의 처리 규칙 [확정 2026-10-15 — Q3]

- 표 없는 모델의 알람은 **이름을 추측하지 않는다**(다른 모델 표를 빌려 쓰지 않음 — 같은 인덱스가 모델마다 다른 이름이라는 사실 `target_definition.md` 5.1 규칙 1).
- C3·탐지 지연의 분자·분모에서 **제외**하고, 모델별 `alarm_type` 별 건수를 `unmapped_alarms.csv` 로 따로 낸다. 그 장비의 포트에서 나온 **AI 인시던트는 그대로 집계**(C1·C2 는 알람명과 무관).
- 표 없는 모델이 테스트망 30대 중 몇 대인지 `alarms --summary` 첫 줄에 출력 → 비중이 크면(예: 장비의 1/3 이상) C3 판정 보류 사유로 보고(판정 규칙 변경은 아님).
- 보완 경로: 사용자가 이름을 알게 되면 수동 매핑 파일 `alarm_name_override.csv`(`model, alarm_type, alarm_name`)로 넣을 수 있다. 수동 매핑은 `name_status = override` 로 구분 표시.

### 7.4 알람명 → 타겟 유형 매핑 입력

- 파일 `validation/realdata/alarm_target_map.csv`(저장소 포함 — 이름은 이미 `target_definition.md` 5.2 에 공개된 것만): 열 `pattern, target_type, grade, source`. `target_type ∈ {CRC증가, 트래픽단절, 광관찰, 제외, 해당없음}`, `grade ∈ {1차, 보조, 사용안함, 관찰참고}`, `source` = 5.2 의 표 ID(A~D).
- 같은 이름이 두 유형이면 행을 두 개(예: OPT-LOS → 트래픽단절/1차, 광관찰/관찰참고).
- 패턴: 정확한 이름 또는 `*` 글롭(예 `FAN-*`). 5.2 의 범위 표기(`OPT-PWR-LOW-1~4`)는 CSV 에서 개별 이름으로 펼친다. **정확한 이름 > 글롭**, 한 이름에 글롭이 둘 이상 걸리면 **로드 시 오류**(모호성은 데이터를 보기 전에 해소).
- 매핑에 없는 이름은 **미분류**. `alarms --summary` 가 미분류 이름·건수 상위 목록을 내어 매핑 갱신(architect, `target_definition.md` 5장)의 입력으로 쓴다. 매핑 갱신은 결과를 본 뒤 하는 일이므로, **갱신 전 실행 결과를 판정 기간 결과로 쓰지 않는다**(9.7).

### 8.6 작업 대용 알람과 작업 CSV

## 9. 분석 출력

### 9.1 트랙 필터

- `--tracks traffic`(기본): AI 재생은 `AnomalyDetector(tracks=('traffic',))`, 베이스라인은 `use_optical=False`. C1~C6 판정 표는 이 결과로만.
- `--observe-optical`: 광 스냅샷이 있는 포트에 대해 광 모델 재생 결과·광 원값·광 알람(D9: OPT-PWR-*, HI-PWR*/LO-PWR*, OPT-LOS) 에피소드를 같은 시간축 CSV 로 낸다(그래프는 U8). **판정 표에는 넣지 않는다.**
- **광 데이터 없음 시 SKIP (2026-10-16, D19)**: 광 스냅샷 행이 0 이면 광 모델 재생·광 원값 출력을 하지 않고 "광 성능 데이터 없음 — SKIP" 을 출력·매니페스트에 기록한다(오류 아님). 이때도 **광 알람 에피소드 요약**(알람명·장비·건수·지속 분포, 광관찰 유형)은 낸다 — 테스트망에서 광은 알람만 존재(D20 의 31/598~600 HI-PWR 계열). 트래픽 재생은 광 데이터와 무관하게 동작해야 한다(`tracks=('traffic',)`).

### 9.2 오프라인 재생 (AI)

- 스냅샷 → 운영과 같은 `AnomalyDetector.detect(df_traffic=…, latest_only=False)`(평가 도구와 같은 호출, `validation/cli/evaluate_model.py:58-61`). 모델 버전·정책은 활성(기본) 또는 `--versions`·`--policy <json>` 로 지정하고 매니페스트에 기록. 대안 정책 재생은 `--policy` 를 바꿔 여러 번 실행.
- 재생 시작 후 포트마다 첫 `required_rows` 구간은 워밍업이라 결과가 없다(C5 분모 정의와 같음, `report_package.md` C5). 재생 구간은 판정 구간보다 **2일 앞**에서 시작하고 앞 2일 결과는 버린다 [제안: 동적 임계치·롤링 규칙 24h 이력 확보].
- 결과 행: `occur_date, ip_addr, cid, lid, alarm(is_anomaly), severity, alarm_level, traffic_score`. 인시던트는 `make_incidents(gap_steps=4)`(`nuisance=False`).
- **공백이 많은 데이터(D17)**: 하루 일부만 수집되는 날이 많아 AI 는 연속 27행이 있는 구간에서만 점수가 나오고, 베이스라인(`rolling_rule` 의 24h 중앙값 등)은 있는 행으로만 계산된다. 세 방법이 **같은 정상 행**을 입력으로 받으므로 비교는 공정하나, 방법마다 "판정할 수 있었던 슬롯"이 다르다 → 방법별 재생 가능 슬롯 비율을 모든 판정 표 머리에 출력한다. 공백을 메우는 보간(운영의 1스텝 보간 외)은 하지 않는다.

### 9.3 베이스라인 재생

- `fixed_threshold`, `rolling_rule` 을 같은 스냅샷·같은 구간·같은 포트로. 광 조건 제거 옵션: 두 함수에 `use_optical: bool = True` 인자를 추가(기본 = 현행 동작, 기존 테스트 불변), 판정 실행은 `False`. `False` 이면 광 열이 없어도 동작해야 한다.
- 베이스라인 임계값(에러 100 / 20, 트래픽 15%)은 **바꾸지 않는다**(시뮬레이터에 맞춰졌을 가능성은 `target_definition.md` 4장의 한정으로 둠). 바꾼 버전이 필요하면 별도 이름으로 추가하고 판정용 베이스라인과 섞지 않는다.

### 9.4 약한 정답 지표 (C3·C4b, 1h/3h/6h)

- 이벤트: 8장의 판정 대상 타겟 이벤트(F5, `join_status` 포함). 방법(AI·고정·롤링)마다:
  - **C3 선행 탐지**: `t0` 이전 `[t0 − 24h, t0 − 15분]` 에 같은 포트 알람이 있었던 이벤트 비율(`report_package.md` C3 그대로). 이벤트 < 20 이면 `판정 보류`.
  - **1h/3h/6h 분할 (R3)**: 선행 탐지된 이벤트의 리드 `t0 − 첫 선행 알람` 으로 `lead ≥ 1h`, `≥ 3h`, `≥ 6h` 비율(분모 = 전체 판정 이벤트, 누적) + 구간별 건수 `[15분,1h) [1h,3h) [3h,6h) [6h,24h]`.
  - C4b: AI C3 > 고정 C3 여부(C3 판정 시에만).
  - **성능 공백 제외 (2026-10-16 추가, 사전 고정 [제안])**: 같은 포트의 정상 성능 슬롯(4.3a 격리 후)이 `[t0 − 6h, t0)` 의 24슬롯 중 **50% 미만**인 이벤트는 C3 분모에서 빼고 `perf_gap` 으로 따로 센다. 이유: 테스트망은 평일 위주·부분 수집이라(D17) 사건 직전 데이터가 없는 이벤트가 많고, 그런 이벤트는 어느 방법도 원리적으로 선행 탐지할 수 없다. 6시간은 리드 분할의 가장 긴 구간(9.4 의 ≥6h)이고, 50% 는 AI 가 연속 27행(약 6.75시간)을 못 채우더라도 베이스라인은 판단할 수 있는 정도의 여유로 정한 값이다(데이터를 보지 않고 정함). 한정: C3 는 "성능 데이터가 있던 이벤트"에 대한 비율로 해석하고 `perf_gap` 건수·비율을 같은 표에 고정 출력(50% 초과 시 보류 사유, 9.7.4). 장비 단위로 성능이 아예 없는 알람 장비(D22, 70 대 60)의 이벤트는 기존 "포트 없음"으로 분류된다.
- 유형별(R8): CRC증가·트래픽단절 각각과 합계. 보조 등급 표는 별도(참고). 표 없는 모델·포트 없음·짧은 에피소드·작업 의심·조인 미검증 건수를 같은 표 아래에 고정 순서로 출력.
- **순환 주의 표시**: ETH-ERR 의 발생 조건을 모르는 동안(질문지 Q1-3) CRC증가의 C3 표에는 "EMS 임계와 규칙 임계가 같은 카운터일 수 있음(`target_definition.md` 5.3)" 문구를 고정 출력.

### 9.5 단절 탐지 지연 (R4)

- 시각 기준(D11 확정): 성능 행 `occur_date = T` 는 `(T − 15분, T]` 구간 값이고, 그 행으로 낸 알람의 시각도 `T` 다. 사건 시각 `t0` 를 처음 담을 수 있는 구간의 끝은 `bin_end(t0) = floor15(t0) + 15분`(`t0` 가 정각 경계이면 다음 구간).
- 트래픽단절 타겟 이벤트마다 같은 포트에서:
  - **탐지**: `bin_end(t0) ≤ occur_date ≤ t0 + 6h` 의 첫 알람. **벽시계 지연** = `occur_date − t0`(분, 최소값은 `bin_end(t0) − t0` 으로 0 초과 15분 이하 — 15분 데이터의 구조적 하한), **스텝 지연** = `(occur_date − bin_end(t0)) / 15분`(0 = 사건이 처음 보이는 구간에서 바로 탐지).
  - **직전 알람**: `t0 − 15분 ≤ occur_date < bin_end(t0)` 의 알람은 사건을 담지 않은 데이터로 낸 알람이다. 탐지로 치되(스텝 지연 0) `pre15 = True` 로 따로 센다(C3 선행 창 `≤ t0 − 15분` 과 겹치지 않음).
  - 방법별 벽시계 지연 중앙값, `≤ 15 / 30 / 60분` 비율, 스텝 지연 분포(0/1/2/3+), 6h 안에 없음(미탐) 비율.
  - **성능 공백 제외 (2026-10-16 추가 [제안])**: 같은 포트의 정상 성능 슬롯이 `[bin_end(t0), t0 + 1h]` 에 **하나도 없으면** 지연 분모에서 빼고 `perf_gap` 으로 센다(사건 뒤 데이터가 없으면 탐지 자체가 불가능). 단절 중 행이 아예 안 생기는 경우와 수집 공백을 구분할 수 없으므로(5.2) 이 건수는 "단절로 행이 사라졌을 가능성"과 함께 해석한다(K17).
  - **절단 `truncated` (개정 4 — dev `report.py` 추가분 승인, 경계 수정)**: 탐지 창 끝 `t0 + 6h` 가 **분석 기간의 끝 `E`** 를 넘는 이벤트는 지연 분모에서 빼고 `truncated` 로 센다. `E` = 개발 실행이면 `J0`, 판정 실행이면 `D`(임의 범위 `START..END` 이면 `END`). 이유: 창의 뒷부분에 재생 결과가 없으므로 그 안의 미탐은 "못 잡음"이 아니라 "볼 수 없음"이다. 판단 순서는 `truncated` → `no_port` → `perf_gap` → 포함(dev 구현 순서 그대로). **dev 구현과의 차이**: 현재 `delay_events` 는 개발 실행에도 `D` 를 넘겨 받는다(`commands.py` `build_report(..., ctx.periods["D"], ...)`) → 개발 실행에서 `J0` 직전 이벤트가 절단되지 않고, 재생 결과가 `J0` 에서 끝나므로 미탐으로 잘못 세진다. 분석 범위의 끝을 넘기도록 고친다. 9.7.1 P5 의 "`D` 를 넘는 이벤트는 절단"을 이 규칙으로 일반화한다. `truncated` 건수는 `no_port`·`perf_gap` 과 함께 표에 고정 출력하고, 9.7.4 의 "트래픽단절 이벤트 < 10" 판단은 절단·공백 제외 **후** 건수로 한다.
  - C3 선행 창은 `t0` 이전만 보므로 절단이 없다.
- C3 선행 창(9.4) `[t0 − 24h, t0 − 15분]` 도 알람 시각 = 구간 끝 기준으로 그대로 쓴다(그 알람의 데이터는 모두 `t0 − 15분` 이전).
- 단절은 "예측"이 아니라 "빠른 탐지" 대상이라(`target_definition.md` 3.2) C3 와 함께 보되 별개 표로 낸다.

#### 9.7.1 기호와 공통 원칙

- **기호**: `S` = 첫 전체 추출 스냅샷의 첫 시각(현재 2026-07-10), `D` = 첫 전체 추출에 들어간 **마지막 데이터 날의 다음 날 KST 자정**(성능 테이블이 10-12 09시에서 끝나 있으므로 그대로면 `D` = 2026-10-13 00:00, D23). `J0` = 판정 시작, 판정 기간 = `[J0, D)`(반열림). 모든 경계는 KST 자정.
- **데이터 일(data day)**: 정상 ETH 행(4.3a 격리 후, 필터 통과)이 1행 이상 있는 날짜. 데이터 없는 날은 **장비 꺼짐**(K17 확정, D23)이라 결측일 뿐 이상이 아니며, 길이는 달력 일이 아니라 데이터 일로 센다. 현재 57 데이터일 / 약 13.5주.
- **P1 — 첫 전체 추출은 빨리 1회**: 롤링 삭제 여부(K13)·수집 지속 여부(K16)는 미확인이지만 대안 1 은 `[S, D)` 만 쓰므로 영향이 없다. 단 롤링 삭제일 경우 오래된 날이 사라질 수 있으므로 계정 준비(4.8 또는 `--allow-write-account`)와 `plan`·소규모 `extract`·`join-check` 확인 후 **곧바로 보존분 전체를 1회 추출**해 스냅샷을 고정한다(약 37만 행, 4.5). 판정 근거의 원본은 이 스냅샷이다.
- **P2 — 개발 기간 최소 28 데이터일 (해석 확정, Q12)**: 판정 모델을 실데이터로 재학습하므로(Q15, 9.7.5a) 학습 28일(`retrain_policy.py:29` `train_days=28`)이 판정 기간과 겹치지 않고 개발 기간 안에 들어가야 한다. 코드의 28일은 **달력 28일**이지만, 테스트망은 달력 28일에 데이터가 약 17일뿐이라(57/95 비율 [추정]) 학습 표본이 부족해진다. 그래서 이 설계는 **"학습 28일" 을 데이터 일 28일로 보수적으로 해석**한다. 그 결과 개발 기간의 달력 길이는 28일보다 길다(약 7주 [추정]). 달력 28일로 해석했다면 개발 약 17 데이터일 / 판정 약 40 데이터일이 되었을 것이나 채택하지 않았다. 매핑·작업 대용 확정은 같은 기간의 알람만 쓰므로 학습 구간과 겹쳐도 된다.
- **P3 — 학습·홀드아웃·판정 겹침 금지**: 판정에 쓰는 모델은 학습 데이터 끝이 `J0` 이전이어야 한다(9.7.5 에서 도구가 강제). P1-1 의 포트 홀드아웃(검증 포트 10%)은 **같은 학습 시간 구간 안의 포트 분할**이라 시간으로 `J0` 이전이면 판정과 겹치지 않는다. 홀드아웃 포트도 판정 기간에는 일반 포트로 포함된다.
- **P4 — 판정 구간은 잠금 전에 분석하지 않는다**: 잠금 전에는 판정 구간에 대해 **AI·베이스라인 재생, `report`, `sample`, 그리고 `alarms --summary`·`--count-only` 까지 실행하지 않는다**. 판정 기간 길이는 9.7.2 의 사전 고정 규칙(데이터 일 수)으로만 정한다. 도구는 잠금 파일이 없을 때 판정 구간과 겹치는 이 하위 명령들을 거부한다. 원본 추출 자체는 판정 구간 포함 언제나 허용(봉인 대상은 "분석"이지 "원본 보관"이 아님).
- **P5 — 이벤트·인시던트의 기간 귀속**: F1~F4 에피소드·타겟 이벤트와 AI 인시던트는 **스냅샷 전체에서 한 번에 만든 뒤**, 타겟 이벤트는 `t0`, 인시던트는 시작 시각으로 기간에 귀속한다(경계에서 잘리지 않음). 판정 재생은 `J0 − 2일` 부터(9.2, 워밍업 결과는 버림 — 그 2일이 장비 꺼짐으로 비어 있을 수 있으며 그대로 둔다). C3 선행 창이 `J0` 이전으로 넘어가도 그 구간 알람은 판정 재생의 워밍업 결과로 계산(입력으로만 쓰인 데이터라 허용). 탐지 지연 창 `t0 + 6h` 가 분석 기간 끝(판정 `D`, 개발 `J0`)을 넘는 이벤트는 지연 분모에서 빼고 **절단** 건수로 보고(9.5 `truncated`, 개정 4).
- **P6 — 동결**: 잠금 파일에 판정용 모델 버전(트랙별)·정책·설정 해시를 기록하고, 판정 실행은 그 버전으로만 재생한다(`--versions` 고정). 운영에서 다른 모델이 승격돼도 판정에는 영향이 없다.

#### 9.7.2 확정안 — 대안 1: 현재 데이터 안 고정 분할 (Q12)

| 항목 | 값 |
|---|---|
| 개발 기간 | `[S, J0)`, **`J0` = 28번째 데이터일의 다음 날 KST 자정** |
| 판정 기간 | `[J0, D)` — 나머지 약 **29 데이터일**(현재 57 기준, 약 7주 [추정]). 잠금 뒤 `J1 = D` 로 고정, 연장 없음 |

| 결과 시점 | 잠금 직후 판정 실행 1회 |
| 이벤트 부족 시 | **C3·C4b 판정 보류 확정**(연장·재선택 없음, 9.7.4) |
| `D` 이후 데이터 | 이 판정에 넣지 않는다. 수집이 계속되면(K16 미답) 그 데이터로 새 판정 기간을 둘지는 **별도 결정**(부록 B 의 대안 2 방식) |

- **채택 이유(사용자 결정)**: 지금 있는 데이터로 결과를 낼 수 있고, 수집 지속 여부(K16)에 의존하지 않는다.
- **이 대안의 약점(그대로 기록)**: (1) 개발 28 데이터일·판정 약 29 데이터일로 둘 다 얇다. (2) 판정 이벤트가 20건에 못 미치면 구제 없이 C3 보류로 끝난다. (3) 판정 기간이 약 7주라 계절·망 구성 변화를 대표하지 못할 수 있다.
- **판정 구간 노출 한정 (대안 1 에 해당)**: 판정 기간 `[J0, D)` 는 **과거 데이터**라 잠금 전 분석을 금지해도 완전히 처음 보는 데이터가 아니다. 구체적으로, **lead 의 2026-10-16 실DB 집계(2.1 D20)로 07-10~10-12 전체의 원 알람 월별 건수(7월 약 1.0만·8월 1.3만·9월 1.6만·10월 ~12일 0.7만)와 상위 `(system_type, alarm_type)` 조합이 이미 알려졌다** — 판정 구간의 원 알람 건수가 월 단위로 일부 노출된 셈이다. 다만 노출된 것은 **원 알람 수준**(깜빡임 병합·매핑·F 규칙 적용 전, 광 HI-PWR 계열 포함)이며, 판정 이벤트(F5) 수와 AI·베이스라인 결과는 노출되지 않았다. 또 사용자가 EMS 화면으로 그 기간의 사건을 기억할 수 있다(도구가 막을 수 없는 지식). 이 노출은 판정 기간 길이·규칙 결정에 쓰이지 않았다(길이는 데이터일 수로만 정함). 판정 결과 보고에 이 한정을 고정 문구로 붙인다.
- **개발 출력을 통한 판정 구간 소량 노출 (개정 4 — reviewer 지적, 구조적 한정)**: 에피소드·이벤트를 스냅샷 전체에서 한 번에 만들기 때문에(P5) 개발 실행 출력에 `J0` 이후 정보가 조금 섞인다. (1) `J0` 이전에 시작해 `J0` 이후까지 이어진 에피소드의 `end`·지속 시간(F3 의 자름은 `D` 기준), (2) `tag_ai_incidents`(9.6 유형별 태깅)가 `J0` 직전 AI 인시던트를 **±60분 안에서 `J0` 이후에 시작한 에피소드**와 매칭해, 판정 구간 첫 약 60분의 에피소드 존재·타겟 유형이 드러날 수 있음, (3) 위 6.1 재분류 건수가 스냅샷 전체 기준이었다면 원 알람 수준 건수. 노출 범위는 `J0` 경계 근처의 에피소드 몇 건과 원 알람 수준 건수이며, 판정 이벤트(F5) 수와 판정 구간의 AI·베이스라인 결과는 드러나지 않는다. **줄이는 조치(dev 요청)**: 개발 실행 출력에서 ① 에피소드 `end` 를 `J0` 에서 잘라 표시하고(원 값은 스냅샷에만), ② 태깅 매칭 대상을 `start < J0` 인 에피소드로 한정한다. 이 조치 전에 만든 개발 출력은 그대로 두고 이 한정에 포함해 보고한다. 판정 결과 보고의 고정 문구에 이 항목을 추가한다.
- **판정 이벤트 수 전망 (사전 예측, 잠금 파일에 기록)**: 판정 이벤트(F5: CRC증가·트래픽단절 1차, F2·F6 제외, 9.4 성능 공백 제외 후)를 **개발 기간에서만** 세어 데이터일당 비율 `r` 을 구한다(`alarms --count-only --range dev`). 판정 20건에 필요한 비율은 `20 / 29 ≈ 0.69건/데이터일`. `r < 0.69` 이면 잠금 파일에 **"C3 판정 보류 예상"** 을 미리 적는다(규칙은 바꾸지 않음 — 예측일 뿐). 원 알람 46,594건(D20)은 깜빡임 병합 전이고 큰 몫이 광 HI-PWR 계열(판정 제외)이라 판정 이벤트 수를 추정할 근거가 되지 않는다 [추정 불가 — 첫 개발 기간 집계로 확인].

#### 9.7.3 절차

1. **전체 추출**(P1) → `S`·`D`·데이터일 목록을 매니페스트에 기록.
2. 데이터일 목록에서 `J0` = 28번째 데이터일의 다음 날을 계산하고, 판정 데이터일 수(≥ 15) 를 확인. **이 시점부터 P4 가 적용**된다(도구가 매니페스트로 `J0` 를 계산해 거부 판단에 씀).
3. 개발 기간에서: `alarms --summary` → 알람명 매핑 CSV·작업 대용 목록 확정, `join-check` 판정, `alarms --count-only --range dev` 로 `r` 산출, 개발 기간 `replay`/`report`(도구 검증·이상 확인용, 정책 선택 아님). **판정 모델 학습**(9.7.5a: 스냅샷 `[S, J0)`, 시드 0, 1회)과 **탐색 모델 학습·탐색 평가**(`[S, X)` 학습 → `[X, J0)` 평가)도 이 단계에서 한다. 정책 선택 아님.
4. **잠금**: `periods lock` 이 잠금 파일(`validation/runs/p1_2/locks/judge_<S>_<D>.json`, 배타적 생성)에 다음을 쓴다 — 대안 ID(`fixed_split_v1`), `S`·`D`·`J0`·판정 데이터일 수, 판정 모델 폴더·버전·`trained_at`·`training_window`·가중치/스케일러/메타 SHA-256·`train_run.json`·학습 CSV 해시(9.7.5a R6), 정책 해시(기본 정책), 설정 해시(매핑 CSV·작업 대용 목록·F1~F8·성능 공백 기준·격리 기준·조인 판정 결과), `r` 과 보류 예상 여부, 노출 한정 문구. 잠금 뒤 이 값들은 **바꾸지 않는다**.
5. **판정 실행 1회**: `report --purpose judge` 가 `[J0, D)` 에 대해 재생·C1~C6·샘플을 한 번에 만든다.

**기간 미확정 상태의 봉인 (개정 4 — reviewer 지적)**: 현재 구현은 `ok = False` 이면 봉인 대상이 없다고 보고 P4 검사를 건너뛴다(`periods.py` `require_unsealed`). 그러면 데이터일이 적은 추출에서 분석한 날짜가, 데이터가 늘어난 새 추출(`S` 같고 `D` 만 늘어남)에서는 판정 구간 `[J0, D')` 에 들어가 **이미 본 데이터로 판정**하게 된다. 다음 규칙을 둔다.
1. **잠정 `J0`**: 데이터일 ≥ 28 이면 `ok = False`(판정 < 15 데이터일)여도 `J0` = 28번째 데이터일 다음 날을 계산하고 **P4 를 `ok = True` 와 똑같이 적용**한다(`[J0, D)` 분석 거부, 잠금은 불가). `S` 가 같고 데이터가 뒤로만 늘면 28번째 데이터일은 바뀌지 않으므로 나중 추출의 `J0` 와 같다.
2. **데이터일 < 28**: 개발·판정을 나눌 수 없으므로 모든 분석은 `purpose: explore` 로만 허용하고, 그 범위는 아래 장부에 남아 **나중에 판정 구간이 될 수 없다**.
3. **분석 장부**: `replay`·`report`·`sample`·`alarms --summary`·`--count-only`·`join-check` 실행은 분석한 시간 범위·`purpose`·스냅샷 `S`/`D`·시각을 `validation/runs/p1_2/analysis_ledger.jsonl` 에 덧붙인다(추가 전용). 판정 실행(`judge`)도 기록한다.
4. **잠금 시 검사**: `periods lock` 은 장부에서 `[J0, D)` 와 겹치는 기록(이전 판정 실행 포함, 다른 `S`·`D` 의 스냅샷 것 포함)이 하나라도 있으면 **거부**한다(fail closed, 측정 전). 따라서 `S` 가 바뀌어(롤링 삭제·추출 시작 변경) `J0` 가 앞당겨지거나, 이미 판정한 기간을 `D` 만 늘린 새 잠금으로 다시 판정하려는 경우도 막힌다. 거부되면 그 스냅샷으로는 판정하지 않고, 겹치지 않는 새 데이터로 판정 기간을 다시 정하는 것은 **별도 결정**(부록 B 방식)이다.
5. 한정: 장부 파일을 지우거나 다른 `runs` 폴더를 쓰는 우회는 막지 못한다(운영자 규율, lessons #38). 장부가 없는 상태에서 잠금하면 경고를 내고 매니페스트에 `ledger_missing` 을 남긴다.

#### 9.7.5 판정 모델의 학습 구간 검사 (P3, 측정 전 거부)

- 판정 재생에 쓰는 각 트랙 모델 메타에서: (a) `trained_at ≤ J0` 이면 통과(학습 시각 이전의 데이터만 쓸 수 있으므로 판정 데이터를 포함할 수 없음 — 레거시 v1 이 여기 해당. 판정 모델은 Q15 로 9.7.5a 재학습 모델만 쓴다), (b) 아니면 `training_window` 의 끝 시각이 있고 `≤ J0` 이면 통과, (c) 그 밖(끝 시각 없음·파싱 불가·`> J0`)은 **거부**(fail closed).

#### 9.7.5a 판정 모델 재학습 절차 (개정 6, 사전 고정)

**R1 — 입력: 스냅샷의 개발 구간만 (DB 미접촉)**
- 학습 입력은 DB 가 아니라 첫 전체 추출 스냅샷(`full1`)이다. 4.3a 격리를 통과한 정상 ETH 행(필터 `signal_type=6`·`time_type=1`, 재생과 같은 입력) 중 **`occur_date < J0`** 인 행만 쓴다. `J0` 00:00 행은 4.7 일 파일 경계대로 판정 쪽이라 쓰지 않는다.
- 구현: 기존 `DataCollector.collect_and_save` 를 그대로 호출하되, DB 대신 **스냅샷 어댑터**를 주입한다(P1-3 `train_operational` 의 `_SimDB` 주입과 같은 방식, `validation/cli/check_promotion.py:158`). 어댑터의 `fetch_traffic` 는 요청 범위와 상관없이 `[S, J0)` 밖의 행을 **돌려주지 않는다**(반열림을 어댑터가 강제). `fetch_optical` 는 빈 프레임(광 0행, D19 — 트래픽 트랙만 학습).
- 자기 알람 이력(의심 구간 A)은 **빈 값**으로 고정한다. 테스트망에서는 우리 시스템이 가동된 적이 없어 운영 경로에서도 비어 있을 것이고, 시뮬레이터 모델의 재생 알람을 A 로 쓰면 시뮬레이터 모델이 학습 데이터를 고르게 된다. EMS 알람(약한 정답)도 학습 제외에 **쓰지 않는다**(정답 누출·레시피 변경). 의심 구간은 모델과 무관한 규칙 B 만으로 정해진다(P1-1 그대로) — 이 사실을 매니페스트와 보고에 적는다.
- `src` 는 수정하지 않는다(어댑터·실행기는 `validation/realdata/`).

**R2 — 학습 설정: 기존 그대로, 탐색 금지**
- `MODEL_CONFIG` 를 **그대로** 쓴다(`config_override` 없음 — P1-3 `RECIPE` 단축 설정도 쓰지 않음). 학습 경로는 `Trainer.train` 그대로: 포트 홀드아웃 10%(`RetrainPolicy.val_port_fraction`, salt 기본 `ptn`), 의심 구간 제외(`suspect_policy = RetrainPolicy()`, 의심 비율 20% 초과 시 중단), 스케일러는 학습 CSV 로만 fit(lessons #25), 임계치는 학습 시퀀스 99.5 백분위(현행).
- **학습 구간 = `[S, J0)` 전체**(28 데이터일, P2 의 "학습 28일을 데이터일로 해석"). 운영의 "최근 28일(달력)"이 아니라 이 구간을 명시해 포트 분할 모드로 넘긴다. 참고: API 의 `date_params`(날짜 분할 모드, `src/api/main.py:361`)는 검증을 날짜로 나누고 포트 홀드아웃이 없어 운영 레시피와 다르므로 쓰지 않는다. 이 설계에서 "날짜 모드 재학습"은 "**학습 구간을 날짜로 고정한 포트 분할 학습**"을 뜻한다.
- 하이퍼파라미터·정제 규칙·홀드아웃 비율·임계 백분위를 **바꾸거나 비교하지 않는다**(사후 선택 방지, lessons #30).
- **시드·횟수 사전 고정**: 학습 난수 `train_seed = 0`(`torch.manual_seed`·`np.random.seed`), 판정 모델은 **1회 학습**. 다른 시드로 추가 학습하지 않는다. 같은 입력·시드에서는 가중치·임계치가 재현된다(P1-5, 같은 장치 기준)는 점을 이용해, 기술적 실패(프로세스 중단·디스크 오류 등 데이터와 무관한 예외)는 **같은 시드로 다시 실행**할 수 있다(결과가 같으므로 선택 여지 없음, 재실행 횟수 기록). 장치(CPU/GPU)와 라이브러리 버전을 메타에 남긴다.
- **학습 실패 (사전 고정)**: 의심 비율 20% 초과 중단, 학습·검증 시퀀스 0, 손실·임계치가 유한하지 않음, 홀드아웃 포트 0 이면 **판정 모델 없음** → AI 판정 불가(9.7.4). 기준을 완화하거나 설정을 바꿔 다시 학습하지 않는다. 성능(알람 수·지표)을 보고 모델을 거부하는 규칙은 두지 않는다(그것도 선택이므로).

**R3 — 저장: 운영 `models/`·레지스트리와 분리**
- 저장 위치 `validation/runs/p1_2/models/<run_id>/`(git 제외). 학습 중에만 `PATHS[ft]` 를 이 폴더로 바꾸고 끝나면 되돌린다(`train_operational` 과 같은 방식, lessons #16). 레지스트리 파일도 이 폴더 안에 따로 생긴다. 운영 `models/`·운영 레지스트리·활성 모델은 **바뀌지 않는다**. 실행 전후 운영 `models/` 의 파일 해시 목록이 같은지 확인해 실행 기록에 남긴다.
- 메타(`Trainer` 가 쓰는 메타 + 실행 기록 `train_run.json`):
  - `training_window` = `{"mode": "port_split", "start": S, "end": J0, "end_exclusive": true, "source": "snapshot", "snapshot": "full1"}` — 9.7.5 (b) 가 `end ≤ J0` 로 통과시킨다(`trained_at` 은 `J0` 보다 늦으므로 (a) 는 해당 없음).
  - `trained_at`, `train_seed`, 장치·`torch` 버전, `MODEL_CONFIG` 해시, 스냅샷 매니페스트 해시, **학습 CSV·검증 CSV 의 SHA-256**과 행 수·포트 수·데이터일 수·최소/최대 `occur_date`, `suspect_stats`, 홀드아웃 포트 목록.

**R4 — 알람 정책: 기본 정책 고정**
- 판정 모델의 알람 정책은 **기본 정책**(`alert_policy=None`, `src/pipeline/alerting.py` 기본값)이다. P1-3 의 오탐 억제형 프리셋도 쓰지 않는다. 실데이터 결과를 보고 정책·임계치를 조정하지 않는다. 정책 튜닝은 판정 **이후** 별도 과제다. `--policy` 인자는 개발 탐색에서만 허용하고 판정 실행에서는 거부한다.

#### 9.7.6 공통 기록·거부 규칙

- 매니페스트에 `purpose: dev|judge` 를 필수로 받고, `judge` 실행은 잠금 파일의 설정 해시와 현재 설정 해시가 같을 때만 진행한다. 같은 잠금에 대한 `judge` 실행이 이미 있으면 거부(측정 전 거부, lessons #38 — 잠금 파일 방식은 P1-3·P1-6 과 같게 `validation/runs/p1_2/locks/`).
- 매핑 CSV 를 개발 기간 결과로 갱신하는 것은 잠금 **전**에만 가능하다. 잠금 뒤 매핑을 바꾸면 해시가 달라져 `judge` 가 거부된다(바꾸려면 새 판정 기간이 필요 — `D` 이후 새 데이터가 쌓인다면 그것으로만, 별도 결정).
- **판정 실행 실패 처리 (개정 4 — reviewer 지적)**: 현재 1회 표식(`claim_judge_run`)은 재생 전에 만들어지므로, 모델 로드 오류처럼 판정 데이터를 보기 전의 실패에도 판정이 소진된다. 원칙은 "판정 구간의 결과가 사람·로그에 보였을 수 있으면 소진, 아니면 되돌림"이다.
  1. **순서 변경**: 표식 전에 할 수 있는 일은 표식 전에 끝낸다 — 모델·스케일러·정책 로드(실제 로드 경로, 잠금 해시 대조 포함), 스냅샷 로드, 출력 폴더 쓰기 가능 확인. 이 단계 실패는 표식이 없으므로 그냥 다시 실행한다.
  2. **표식에 단계 기록**: 표식 파일에 `phase` 를 둔다 — `claimed`(표식 직후) → `computing`(판정 구간 데이터가 처음으로 모델·베이스라인에 들어가기 직전) → `completed`(모든 출력 작성 후, 출력 파일 해시 기록).
  3. **되돌림 허용 (자동)**: `phase = claimed` 에서 난 예외(예: 표식 직후 메모리·파일 오류)는 도구가 표식을 `judge_<S>_<D>.aborted_<n>.json` 으로 이름을 바꾸고(삭제 아님, 오류 내용 포함) 재실행을 허용한다. 횟수와 오류는 최종 판정 보고에 적는다.
  4. **재시도 1회 (사람 승인)**: `phase = computing` 에서 실패하고 `completed` 가 아니면, 부분 출력이 있었을 수 있으므로 자동 되돌림은 없다. `periods retry-judge --reason "<사유>"` 로 **1회만** 다시 실행할 수 있다. 조건: 잠금의 설정·모델·정책 해시가 그대로일 것(도구 검사), 실패 전후 도구 코드의 git 커밋을 표식에 기록, 수정 커밋이 판정 규칙·기준값(10장)·분류 규칙(6.1)을 건드리지 않았음을 reviewer 가 diff 로 확인, 실패 실행의 부분 출력은 지우지 않고 목록으로 남김. 두 번째 실패면 **소진** — 이 잠금으로는 판정하지 않고 보고한다(새 판정 기간은 별도 결정).
  5. **완료 후**: `completed` 뒤에는 재실행하지 않는다. 완료 후 도구 버그가 발견되면 원 결과를 그대로 남기고, 사용자 승인으로 `judge-correction` 실행 1회를 따로 만들 수 있다 — 두 결과를 모두 보고하고 정정 결과에 "사후 정정" 한정을 붙인다(수정 범위는 4 와 같은 조건).
  6. 사용자의 Ctrl+C 등 중단도 그 시점 `phase` 로 같은 규칙을 적용한다. 재생·지표 계산은 같은 입력에서 결정적이므로 재실행이 다른 값을 고를 여지는 없고, 남는 위험은 실패 사이에 코드를 바꾸는 것이라 4 의 diff 확인으로 막는다.
- 섀도 운영 판정 기간(`report_package.md` 5.3)은 이 과거 이력 판정과 **별개**다.
- 한정: (1) 판정 기간이 약 29 데이터일(약 7주)이라 계절·망 구성 변화를 대표하지 못할 수 있다. (2) 테스트망의 사건 빈도를 모르므로 C3 보류 가능성이 크다(9.7.2 전망). (3) 판정 구간의 원 알람 월별 건수가 lead 집계로 일부 노출됐다(9.7.2). (4) 롤링 삭제 여부(K13)·수집 지속 여부(K16)는 미확인이나 대안 1 의 판정에는 영향이 없다.

### 9.8 현장 검토 샘플과 채점 (C1·C2·C4a)

- `sample`: `report_package.md` 4.3 그대로 — 방법별 주간 할당량(개발 30/10/10, 판정 50/15/10), 심각도 층화 무작위(시드 인자 필수, 기록), 포트당 최대 3건, 세 방법을 섞은 블라인드 ID, 같은 포트·시간 겹침 인시던트는 1행으로 라벨 공유(행이 대표하는 방법 목록은 별도 비공개 키 파일에만). 검토 열: `분류(유효-장애/유효-예방/정상 변동/오탐/판단 불가), 근거 메모`. 참고 정보 열: 같은 포트 ±24h EMS 알람명 목록, 작업 의심 여부(8.6) — **분류를 미리 채우지 않는다**.
- `score-review`: 검토 CSV + 비공개 키 → 방법별 유효율 점추정·Wilson 95%(z = 1.96), 판단 불가 비율(30% 초과 경고), 판정 가능 샘플 수(≥ 100 여부), C1 = 인시던트/포트·일 × (1 − C2 점추정), C4a = 인시던트 수 × 유효율 구간으로 충족/동률/미충족.

### 9.9 C5 (라이브 결과, `live`)

- 읽기 전용으로 `anomaly_detection` 을 조회(C5 는 라이브 가동 구간만, `report_package.md` C5). C5a = 저장 행 / 처리 대상 행(스냅샷에 `DataProcessor` 를 적용해 윈도우가 생기는 행), C5b = `detect_time − occur_date` 분포·30분 이내 비율, C5c 근거 = 결과가 1시간 이상 빈 구간.
- 라이브와 오프라인 재생의 알람 일치율도 출력(배치-스트리밍 동등성의 실데이터 재확인, lessons #26). 단 2.2-2 의 필터 차이가 있으면 입력이 달라 일치하지 않을 수 있다 — Q1 결정 전에는 참고치.
- 이 하위 명령도 읽기 전용(권한 검사 4.1 동일)이다. `anomaly_detection` 은 Q11 결정으로 같은 DB(같은 스키마의 별도 테이블 또는 별도 스키마)에 있다. 기본 = 같은 접속 설정·같은 스키마, 별도 스키마면 `--result-schema <이름>`(정규식 `^[A-Za-z0-9_]+$` 검증 후 백틱 한정, 그 스키마에도 SELECT 권한 필요 — 4.8-1).

## 13. 위험·한정·미검증

1. **약한 정답의 한계**: EMS 알람은 장애 그 자체가 아니다. 발생 조건(D10: 임계 설정 없음)을 모르므로 C3 는 "EMS 가 알린 사건을 먼저 울렸는가"일 뿐이며, ETH-ERR 과 우리 규칙이 같은 카운터라면 순환이다(9.4 고정 문구).
2. **조인 근거는 데이터 일관성뿐**(개정 5): 보정 키(알람 cid − k)는 개발 구간의 매칭률·address 일치(6.2)로 정했고 **현장 대조(M1)는 하지 못했다** — 보고 고정 문구. 매칭률 85.4% 는 나머지 약 15% 의 알람이 성능 포트를 찾지 못한다는 뜻이며, address 가 둘 다 틀린 체계적 오류는 이 검사로 잡을 수 없다. J3 는 수집 공백 때문에 판별력이 낮아 방향 확인만 한다. J4·J2 기준값(0.8·0.9)은 개발 구간 값을 본 뒤 정했다. J 결과가 `failed`/`degraded` 면 C3·탐지 지연은 판정에 쓰지 않는다. 행 분류(6.1, 개정 4·6)는 dev 스냅샷에서 본 표기(`SYSTEM`·`(256,255)`·슬롯만 있는 address·`MAIN-Pn`·비포트 표기)에 맞췄다. `MAIN-Pn` 은 사용자 확인과 개발 구간 키 대조로 포트가 되었으나(개정 6), 그 밖의 비포트 표기(팬 등) 중 실제 포트가 있으면 판정에서 빠진다(과소 계수, 성능 키 매칭 건수로 크기를 보임). 판정 구간에 개발 구간에 없던 표기가 나오면 규칙 8 로 unit 이 된다.
3. **8장 규칙은 데이터 없이 정한 값**이다. 해상도·일관성 논리로 정했으나 실제 알람 패턴(깜빡임 주기, 지속 분포)에 맞는지 모른다. 감도(15분·4h 병합) 건수를 참고로 내고 판정에는 쓰지 않는다.
4. **판정 모델의 한계**(개정 6): 판정 모델은 28 데이터일·부분 수집(D17) 데이터로 1회 학습한 모델이라 학습 표본이 얇고, 시드 1개라 학습 난수에 따른 편차를 모른다(P1-3 에서 시드 간 편차가 컸음, lessons #36). 의심 구간은 모델 무관 규칙 B 뿐이라 개발 기간의 실제 장애가 학습에 섞일 수 있다(EMS 알람은 제외에 쓰지 않음). 정책은 기본값 고정이라 실데이터에 맞춘 정책보다 불리할 수 있다 — 그래도 판정 전에는 튜닝하지 않는다. 재생 결과가 극단이면 그대로 보고한다. 탐색 모델(21 데이터일)의 결과는 판정 모델과 같은 모델의 결과가 아니다. 시뮬레이터 학습 모델(K12)은 판정에 쓰지 않는다.
5. **운영 입력과 도구 입력의 차이**(2.2-2): Q1 결정 전에는 라이브(C5) 와 재생의 일치율이 낮아도 원인이 필터일 수 있다.
6. **30대 규모**: C2 샘플 ≥ 100, C3 이벤트 ≥ 20, C6 중앙값 ≥ 10 이 채워지지 않아 판정 보류가 날 수 있다(plan.md P0-3 재점검 지점). 도구는 보류를 보류로 낸다.
7. **광은 판정 제외**: 광 알람(D9)이 있어도 통계 판정하지 않는다(테스트망은 광 성능 0행 — 11b).
8. **데이터 취급**: 스냅샷·샘플에는 IP·국소명이 들어간다. `validation/runs/` (git 제외) 밖으로 복사하지 않는다. 알람명 JSON 저장 위치는 Q2.
9. **미검증**: 실DB 에서 한 번도 실행하지 않은 설계다. 4.5 의 예상 규모(포트 2,000 가정, 행당 압축 크기, 쿼리 시간)는 모두 [추정]이며 `plan` 출력으로 대체해야 한다. 2.3 의 K 항목은 모두 첫 실행 출력으로 확인해야 한다. MySQL 5.7.43 의 `SET SESSION TRANSACTION READ ONLY`·`MAX_EXECUTION_TIME`·`SHOW GRANTS FOR CURRENT_USER()` 출력 형식은 문서 기준이며 실DB 에서 확인하지 않았다.
10. **현재 계정은 root**(D12): 읽기 전용 계정을 만들거나 `--allow-write-account` 를 명시하기 전에는 도구가 실행되지 않는다(의도된 기본 동작). 플래그 사용 시 서버 쪽 권한 방어선이 없고 쓰기 계정 비밀번호가 분석 PC 환경변수에 놓인다(4.1, 사용자가 테스트망 한정으로 수용 — D15).
11. **데이터량의 제약(D14·D17)**: 테이블은 약 3개월이지만 데이터일은 57일, 포트·일당 행도 96 보다 적다(평일 위주·부분 수집). 대안 1 은 개발·판정을 같은 57일에서 나누므로 둘 다 얇고(개발 28 / 판정 약 29 데이터일), 사건 빈도를 몰라 C3 보류 가능성이 크다(9.7.2 전망·9.7.4). 성능 공백 이벤트가 분모에서 빠지므로 C3 는 "성능 데이터가 있던 이벤트"에 대한 비율이다(9.4). 판정 구간은 잠금 전 분석·건수 집계를 모두 금지해 개정 1 의 "봉인 불완전" 한정은 없앴으나, **lead 의 10-16 집계로 07-10~10-12 의 원 알람 월별 수·상위 종류가 이미 노출**되었고(2.1 노출 기록) 사용자가 EMS 화면으로 그 기간 사건을 알고 있을 수 있다 — 확정한 대안 1 의 판정 기간에 해당하는 한정이다(9.7.2 에 고정 문구로 기록, 판정 결과 보고에도 붙임).
11a. **시각 격리(4.3a)**: ETH 행의 10.6% 가 격리된다(D18). 격리가 특정 장비·시기에 몰리면 그 부분이 성능 공백이 되어 결과를 기울일 수 있다 — `quarantine_heavy` 목록으로 보인다. ±1.5시간 폭은 lead 제안값이며 근거 데이터로 검증하지 않았다.
11b. **광**: 테스트망 광 성능 0행(D19)이라 광 관찰은 알람 요약만 가능하다. `target_definition.md` 의 "광 데이터 2~3대분" 서술은 이 테스트망 DB 에는 해당하지 않는다(문서 수정은 별도 — 이 설계서만 수정 범위).
12. **결과 쓰기 경로**(2.2-9): Q11 로 테스트망에서는 같은 DB 에 결과를 써도 된다. 남는 위험은 같은 이름 테이블 충돌(4.9 가 점검)과, 이 결정이 납품 현장 DB 에 그대로 적용되지 않는다는 점이다(현장 결정은 별개 — 부록 A).
